## 0. 큰 그림: 이 직무가 다루는 흐름

```
유저 행동
  ↓
① 이벤트 로깅        "무엇을 기록할까" (설계·구현)
  ↓
② 파이프라인         "어떻게 모으고, 저장하고, 가공할까"
  ↓
③ 데이터 품질        "그 데이터를 믿을 수 있나" (전 단계에 걸침)
  ↓
④ 지표·분석          "숫자로 무엇을 알 수 있나" (퍼널, 리텐션, CAC, ROAS)
  ↓
⑤ 실험(A/B)          "바꾸면 정말 좋아지나"
  ↓
실행·자동화          마케팅 툴, CRM, AI 에이전트가 데이터를 받아 동작
```

**예시 시나리오**

1. PM이 "가입하다 이탈하는 유저가 많다"고 문제를 제기합니다.
2. 엔지니어가 가입 단계별 이벤트가 제대로 남고 있는지 확인하고, 없으면 설계해서 심습니다. (①)
3. 이벤트가 파이프라인을 타고 분석 테이블에 쌓입니다. (②)
4. 퍼널로 보니 "이메일 인증 단계"에서 가장 많이 이탈합니다. (④)
5. 인증 단계를 단순화한 화면을 A/B 테스트합니다. (⑤)
6. 결과 데이터가 틀리지 않았는지 검증합니다. (③)
7. 효과가 검증되면 전체에 적용하고, 이탈한 유저에게 Braze로 리마인드 메시지를 자동 발송합니다.

## 1. 이벤트 로깅

### 1.1 이벤트란

**유저가 한 행동 1건을 기록한 데이터**입니다. 구성은 "누가, 언제, 무엇을, 어떤 맥락에서"입니다.

```json
{
  "event_name": "purchase_completed",
  "timestamp": "2026-09-21T14:03:22+09:00",
  "anonymous_id": "a1b2c3",
  "user_id": "u_1029",
  "properties": {
    "order_id": "O-7781",
    "amount": 32000,
    "payment_method": "card"
  },
  "context": { "platform": "ios", "app_version": "3.2.1" }
}
```

**백엔드 로그와의 차이**: 액세스 로그는 시스템 관점(`POST /orders 200 45ms`)이고, 이벤트는 비즈니스 관점(**유저가 주문을 완료했다**)입니다. 목적이 장애 추적에서 행동 분석으로 바뀝니다.

### 1.2 이벤트 속성 대 유저 속성

| |이벤트 속성 (event properties)|유저 속성 (user properties)|
|---|---|---|
|의미|**그 행동의 순간** 정보|**유저 자체의 상태**|
|예시|결제 금액, 상품 ID, 버튼 위치|가입일, 회원 등급, 유입 채널, 국가|
|변하는가|이벤트마다 다름|시간에 따라 갱신됨|
|용도|행동의 상세 분석|**세그먼트**(유저 그룹 나누기)|

세그먼트 예: "유료 회원 중 D7 리텐션", "광고로 유입된 유저의 구매 전환율".

### 1.3 이벤트 네이밍과 트래킹 플랜

같은 행동이 `click_buy`, `buy_click`, `purchaseBtn`처럼 제각각 기록되면 합산이 불가능해집니다. 그래서 규칙을 정합니다.

- 권장 형태: **객체 + 과거형 동사**, snake_case (`signup_completed`, `cart_item_added`)
- 이벤트 이름은 적게 유지하고 세부는 속성으로 구분합니다. `click_banner_1`, `click_banner_2`처럼 나누지 않고 `banner_clicked` + `banner_id` 속성으로 씁니다.

**트래킹 플랜(택소노미)** 은 이벤트명, 발생 시점, 속성, 타입, 담당자를 적어 둔 문서입니다. 백엔드의 **API 명세서 또는 DB 스키마와 같은 계약서**이고, 앱·웹·서버 개발자가 같은 기준으로 구현하게 합니다.

### 1.4 유저 식별과 Identity Stitching

로그인 전에는 누구인지 모르므로 브라우저나 기기에 **익명 ID(anonymous_id)** 를 부여합니다. 로그인하면 **user_id**가 생깁니다.

```
10:00  비로그인 방문, 상품 조회      anonymous_id = A
10:05  회원가입·로그인               user_id = U1
       → "A와 U1은 같은 사람"이라고 연결 (identity stitching)
```

연결하지 않으면 한 사람이 두 명으로 집계되어 유저 수가 부풀고, **가입 전 유입 경로(어떤 광고를 보고 왔는지)** 를 가입자에게 귀속하지 못합니다. 기기가 여러 개인 경우(폰과 PC)도 user_id로 묶어야 합니다.

### 1.5 세션

**연속된 행동을 하나의 방문으로 묶은 단위**입니다. GA4는 기본적으로 30분간 활동이 없으면 세션이 끝난 것으로 봅니다(설정 변경 가능). 세션 정의는 도구마다 조금씩 달라서, **도구 간 숫자가 안 맞는 흔한 원인**입니다.

### 1.6 클라이언트 대 서버 사이드 트래킹

||클라이언트 (앱/브라우저에서 전송)|서버 사이드 (백엔드에서 전송)|
|---|---|---|
|잡을 수 있는 것|화면 조회, 클릭, 스크롤 등 UI 행동|결제, 가입 완료 등 서버에서 확정되는 사실|
|정확도|낮음 (광고 차단, 네트워크 끊김, 앱 강제 종료, 브라우저 쿠키 제한으로 유실)|높음 (DB 트랜잭션과 함께 발생)|
|주의점|유실·중복|화면 행동은 알 수 없음|

**실무 원칙**: 돈과 직결되거나 절대 틀리면 안 되는 이벤트(결제 완료, 환불, 구독 갱신)는 **서버에서**, UI 행동은 클라이언트에서 남기는 **하이브리드**로 갑니다. 서버에서 이벤트를 남길 때는 **DB 커밋은 성공했는데 이벤트 발행이 실패하는(또는 반대) 경우**를 다뤄야 하며, 백엔드의 아웃박스 패턴이나 재시도와 같은 문제입니다.

### 1.7 SDK와 태깅(GTM)

- **SDK**: 분석 도구가 제공하는 라이브러리를 앱·웹 코드에 설치하고, 코드에서 `track("event", {...})`를 호출합니다. 코드 배포가 필요합니다.
- **태깅(GTM, Google Tag Manager)**: 웹 페이지에 **관리 콘솔에서 추적 코드(태그)를 붙이고 떼는** 도구입니다. "이 버튼이 클릭되면(트리거) 이 이벤트를 GA4로 보내라(태그)"를 코드 배포 없이 설정합니다. 웹 페이지가 GTM에 데이터를 넘기는 통로가 `dataLayer`(JS 객체)입니다.

마케터가 자주 바꾸는 웹 추적은 GTM, 앱과 핵심 이벤트는 SDK·서버로 나누는 경우가 많습니다.

## 2. 데이터 저장과 파이프라인

### 2.1 OLTP 대 OLAP

| |OLTP (서비스 DB)|OLAP (분석 DB)|
|---|---|---|
|목적|서비스 운영 (주문 저장, 회원 조회)|분석 (매출 집계, 퍼널)|
|쿼리|소량 행을 빠르게 읽고 쓰기|대량 행을 훑어서 집계|
|저장 방식|행(row) 단위|**열(column) 단위**|
|대표|MySQL, PostgreSQL|BigQuery, Redshift, Snowflake|

**서비스 DB에서 직접 분석하면 안 되는 이유**: 큰 집계 쿼리가 운영 DB를 느리게 하고, 분석에 맞는 구조도 아닙니다. 그래서 분석용 저장소로 데이터를 **옮겨서** 씁니다. 열 단위 저장은 "수억 행에서 `amount` 컬럼만 합산"할 때 그 컬럼만 읽으면 되어 훨씬 빠릅니다.

### 2.2 데이터 레이크 대 웨어하우스

- **데이터 레이크**: 원본 파일을 구조 없이 그대로 쌓는 저장소 (예: S3의 JSON·Parquet 파일)
- **데이터 웨어하우스**: 분석하기 좋게 테이블로 구조화된 저장소 (BigQuery 등)

흔한 구성은 원본을 레이크(S3)에 쌓고 웨어하우스로 적재해 분석합니다.

### 2.3 ETL 대 ELT

- **ETL**: 추출(Extract) → **변환(Transform)** → 적재(Load). 변환 후 저장합니다.
- **ELT**: 추출 → **적재** → 변환. 원본을 먼저 웨어하우스에 넣고 그 안에서 SQL로 변환합니다.

최근에는 ELT가 흔합니다. 웨어하우스 성능이 좋아졌고, **원본이 보존되어 변환 로직을 고쳐도 다시 계산하면 되기** 때문입니다.

**데이터 계층**: 조직마다 이름은 다르지만 보통 이렇게 나눕니다.

```
raw     원본 그대로 (손대지 않음)
  ↓
staging 중복 제거, 타입·타임존 정리
  ↓
mart    분석 목적별 집계 (일별 매출, 퍼널, 코호트)
```

### 2.4 배치 대 스트리밍

| |배치|스트리밍|
|---|---|---|
|방식|모아서 주기적으로 처리 (매일 새벽 등)|이벤트 도착 즉시 처리|
|적합|일별 리포트, 대시보드|실시간 알림, 즉시 메시지 발송, 이상 탐지|
|복잡도|낮음|높음 (순서·지연·상태 관리)|

**"정말 실시간이어야 하는가"를 먼저 묻습니다.** 대부분의 분석은 하루나 한 시간 단위 배치로 충분합니다.

### 2.5 Kafka

**메시지를 쌓아 두고 여러 소비자가 각자 읽어 가는 분산 로그 시스템**입니다.

- **토픽(topic)**: 메시지 종류별 채널 (예: `purchase_events`)
- **프로듀서**가 쓰고, **컨슈머**가 읽습니다.
- **파티션**: 토픽을 쪼갠 단위. 병렬 처리의 기본 단위이고, **순서는 파티션 안에서만 보장**됩니다.
- **오프셋**: 컨슈머가 어디까지 읽었는지의 위치. 오프셋을 되돌리면 **과거 메시지를 재처리**할 수 있습니다(보존 기간 내).
- **컨슈머 그룹**: 같은 그룹 안에서는 파티션을 나눠 읽고, 다른 그룹은 각자 독립적으로 전체를 읽습니다.

**왜 쓰는가**: 이벤트가 몰려도 큐가 완충하고, 수집 서버와 후속 처리를 분리하며, 여러 소비처(웨어하우스 적재, 실시간 알림, 에이전트)가 같은 데이터를 각자 가져갈 수 있습니다. 전달 보장은 보통 "최소 1회"라서 **중복이 생길 수 있고, 소비 측을 멱등하게 만드는 것**이 실무 과제입니다.

### 2.6 Airflow

**작업들의 순서, 스케줄, 재시도를 관리하는 오케스트레이터**입니다. 데이터를 직접 처리하지 않고 "무엇을 언제 어떤 순서로 실행할지"를 관리합니다. Jenkins가 빌드·배포 단계를 관리하는 역할과 비슷합니다.

- **DAG**: 작업 간 의존 관계를 방향성 있는 그래프로 정의한 것
- **Task**: DAG 안의 개별 작업 (적재, 변환, 검증 등)
- 실패 시 재시도, 알림, 의존 작업 대기를 제공합니다.

```python
with DAG("daily_events", start_date=datetime(2026, 9, 1),
         schedule="@daily", catchup=False,
         default_args={"retries": 3, "retry_delay": timedelta(minutes=5)}):
    extract = PythonOperator(task_id="extract", python_callable=extract_fn)
    transform = PythonOperator(task_id="transform", python_callable=transform_fn)
    validate = PythonOperator(task_id="validate", python_callable=validate_fn)

    extract >> transform >> validate   # 순서 정의
```

**핵심 개념 두 가지**

- **논리적 날짜(logical date / data interval)**: "이 실행은 9/20 하루치 데이터를 처리한다"는 기준 날짜입니다. 실행 시각이 아니라 **처리 대상 날짜로 작업을 정의**하므로 몇 번을 재실행해도 같은 범위를 처리합니다.
- **백필(backfill)**: 과거 기간의 작업을 다시 돌리는 것. 로직 버그를 고친 뒤 지난 3개월을 재계산할 때 씁니다.

### 2.7 멱등성 (파이프라인의 핵심 설계 기준)

**같은 작업을 몇 번 실행해도 결과가 같아야 합니다.**

- 나쁜 예: 9/20 집계를 재실행할 때마다 결과 테이블에 행을 **추가(append)** → 재시도할 때마다 숫자가 두 배가 됩니다.
- 좋은 예: 9/20 파티션을 **삭제 후 다시 적재하거나 덮어쓰기** → 몇 번을 돌려도 같은 결과입니다.

정기결제 배치에서 중복 결제를 막는 고민과 같은 종류의 문제입니다.

### 2.8 SQL, Pandas, PySpark

- **SQL**: 웨어하우스 안에서 변환·집계하는 기본 도구입니다.

```sql
SELECT event_name, COUNT(DISTINCT user_id) AS users
FROM events
WHERE event_date = '2026-09-20'
GROUP BY event_name;
```

- **Pandas**: Python의 표 형태(DataFrame) 데이터 처리 라이브러리입니다. 필터링, 그룹 집계, 조인에 씁니다.

```python
steps = ["visit", "signup_completed", "purchase_completed"]
users = {s: df.loc[df.event_name == s, "user_id"].nunique() for s in steps}
```

- **PySpark**: Pandas와 비슷한 DataFrame 개념을 **여러 머신에 분산**해서 처리합니다. 데이터가 한 머신의 메모리를 넘을 때 씁니다.

(위 예시는 단계별 유저 수만 셉니다. **순서까지 고려한 퍼널**은 윈도우 함수 등이 필요합니다.)

## 3. 데이터 품질

백엔드는 에러가 나면 바로 알지만, 데이터는 **에러 없이 틀릴 수 있다**는 점이 핵심입니다.

|품질 차원|의미|문제 예시|탐지 방법|
|---|---|---|---|
|완전성|있어야 할 데이터가 있는가|이벤트 누락, 필수 속성 null|이벤트 볼륨 전일·전주 대비 급변 알림, null 비율|
|유일성|중복이 없는가|재시도로 같은 결제 이벤트 2건|이벤트 ID 기준 중복 검사|
|유효성|형식과 값이 맞는가|금액이 문자열, 음수|스키마 검증, 값 범위 검사|
|적시성|제때 도착하는가|파이프라인 지연, 지연 도착 이벤트|최신 데이터 시각 모니터링|
|일관성|소스 간 일치하는가|서버 결제 합계와 분석 도구 매출 불일치|소스 간 대조|
|정확성|실제 사실과 맞는가|타임존 오류로 날짜가 하루 밀림|샘플 검증|

**조용한 실패 사례**: 앱 업데이트 후 `purchase_completed`의 `amount` 속성이 `amt`로 바뀌었습니다. 파이프라인은 에러 없이 성공하지만 대시보드 매출이 갑자기 0에 가까워지고, 그 숫자를 보고 광고 예산을 줄이는 결정이 내려집니다. 그래서 각 단계에 **자동 검증과 알림**이 필요합니다. dbt tests나 Great Expectations 같은 도구가 대표적입니다.

**지연 도착(late-arriving)**: 오프라인이던 앱이 이벤트를 하루 뒤에 보내면 이미 집계가 끝난 날짜의 숫자가 바뀌어야 합니다. 이벤트에는 발생 시각(event time)과 수신 시각(ingestion time)을 **둘 다** 기록하고, 최근 며칠은 재계산하는 방식으로 대응합니다.

## 4. 핵심 지표

### 4.1 AARRR 퍼널

|단계|질문|대표 지표|
|---|---|---|
|Acquisition 유입|어디서 오는가|채널별 유입, CAC|
|Activation 활성화|첫 가치를 경험했는가|가입 완료율, 온보딩 완료율|
|Retention 유지|다시 오는가|D1/D7/D30 리텐션|
|Revenue 수익|돈을 쓰는가|ARPU, LTV, 전환율|
|Referral 추천|다른 사람을 데려오는가|추천 가입 비율|

### 4.2 지표 정의와 계산 예

|지표|정의|식|
|---|---|---|
|전환율|목표 행동을 한 비율|전환 유저 / 대상 유저|
|CAC|고객 1명을 얻는 데 든 비용|마케팅 비용 / 신규 고객 수|
|ROAS|광고비 대비 광고로 발생한 매출|광고 매출 / 광고비 × 100%|
|ARPU|유저당 평균 매출|기간 매출 / 활성 유저 수|
|LTV|고객 1명이 생애 동안 가져오는 가치|예: ARPU × 평균 유지 기간 (또는 이익 기준)|
|리텐션 Dn|가입 n일 후 재방문 비율|n일차 재방문 유저 / 코호트 인원|
|이탈률(churn)|떠난 비율|이탈 유저 / 기간 초 유저|
|DAU / MAU|일간·월간 활성 유저|DAU/MAU가 높으면 자주 쓴다는 의미|

**계산 예시**

- 광고비 1,000,000원 → 신규 가입 200명 → **CAC = 5,000원**
- 그중 40명 구매(**전환율 20%**), 평균 결제 50,000원 → 광고 매출 2,000,000원 → **ROAS = 200%**

주의할 점이 두 가지입니다.

- 위 CAC는 "가입자" 기준이고, "결제 고객" 기준으로 세면 1,000,000 / 40 = 25,000원입니다. **"고객"을 무엇으로 정의하는지는 팀마다 다르므로** 반드시 합의해야 합니다.
- ROAS는 **매출** 기준이라 마진을 반영하지 않습니다. ROAS 200%여도 원가가 높으면 손해일 수 있습니다.

**LTV와 CAC의 관계**: 고객 1명을 얻는 데 든 돈(CAC)보다 그 고객이 가져오는 가치(LTV)가 커야 사업이 남습니다. 경험칙으로 LTV/CAC가 3 이상이면 건강하다고 보는데, 업종에 따라 다릅니다.

**이 지표가 파이프라인과 연결되는 이유**: ROAS를 계산하려면 **광고 플랫폼의 비용 데이터**와 **서버의 결제 데이터**를 같은 캠페인 단위로 조인해야 합니다. 서로 다른 소스를 합치는 작업이 Growth Engineer의 실무입니다.

### 4.3 퍼널 분석 대 코호트 분석

**퍼널**: 단계별로 얼마나 넘어가고 어디서 빠지는지를 봅니다. 답하는 질문은 "어느 단계가 병목인가"입니다.

```
방문 10,000 → 가입 시작 2,000 (20%) → 가입 완료 1,200 (60%) → 첫 구매 300 (25%)
전체 전환율 = 300 / 10,000 = 3%
```

**코호트**: **같은 시점(또는 같은 조건)에 시작한 유저 그룹**을 시간에 따라 추적합니다. 답하는 질문은 "시간이 지나며 유지되는가, 개선 후 들어온 유저는 더 잘 남는가"입니다.

|가입일|인원|D1|D7|D30|
|---|---|---|---|---|
|9/1|1,000|40%|20%|10%|
|9/8 (온보딩 개선 후)|1,100|48%|27%|15%|

전체 평균으로는 안 보이는 "개선의 효과"를 코호트끼리 비교해서 봅니다.

**리텐션 정의 주의**: "정확히 7일째에 왔는가(N-day)"와 "7일 이후 언제든 왔는가(unbounded)"가 다릅니다. 도구마다 기본값이 달라서 숫자가 안 맞는 원인이 됩니다.

### 4.4 UTM과 어트리뷰션

- **UTM**: 링크 뒤에 붙이는 출처 표시 파라미터입니다. 예: `?utm_source=instagram&utm_medium=paid&utm_campaign=fall_sale`
- **어트리뷰션**: 가입·구매의 **공을 어느 광고(터치포인트)에 돌릴지** 정하는 규칙입니다. 마지막 접점에 100%를 주는 last-click, 처음에 주는 first-click, 여러 접점에 나누는 멀티터치가 있습니다. 어트리뷰션 규칙에 따라 채널별 ROAS가 달라집니다.

## 5. A/B 테스트

### 5.1 개념

유저를 무작위로 두 그룹으로 나눠 **한쪽에만 변경을 적용하고, 지표 차이가 우연이 아닌지** 판단하는 실험입니다.

- **대조군(control)**: 기존 그대로, **실험군(variant)**: 변경 적용
- **무작위 배정**이 핵심입니다. 그래야 두 그룹의 차이가 변경 때문이라고 말할 수 있습니다.
- 배정 단위는 보통 유저입니다. 같은 유저가 매번 다른 버전을 보면 안 됩니다.

### 5.2 통계 용어

|용어|뜻|
|---|---|
|귀무가설 (H0)|"두 그룹은 차이가 없다" (기본 가정)|
|대립가설 (H1)|"차이가 있다"|
|**p-value**|H0가 참이라고 가정할 때, 관측된 것 이상으로 극단적인 차이가 **우연히** 나올 확률|
|유의수준 (α)|미리 정한 기준 (보통 0.05). p < α면 "통계적으로 유의하다"고 판단|
|검정력 (power)|실제로 차이가 있을 때 그것을 잡아낼 확률 (보통 80%)|
|MDE|잡아내고 싶은 **최소 효과 크기** (예: 전환율 10% → 11%)|
|표본 크기|기준 전환율, MDE, α, 검정력이 정하는 그룹당 필요 인원|

**p-value 오해 주의**: p = 0.03은 "실험군이 더 좋을 확률이 97%"가 **아닙니다.** "차이가 없는데도 이 정도 차이가 우연히 나올 확률이 3%"라는 뜻입니다.

**직관**: α = 0.05는 "실제로는 효과가 없는데 있다고 잘못 결론 내릴 위험을 5%까지 허용한다"는 의미입니다.

### 5.3 표본 크기 감각

기준 전환율 10%에서 11%(상대 10% 향상)를 α 0.05, 검정력 80%로 잡으려면 **그룹당 약 15,000명**이 필요합니다. 잡으려는 차이가 절반(10%→10.5%)이 되면 필요한 표본은 **약 4배**로 늘어납니다. 그래서 작은 서비스에서는 작은 개선을 검증하기가 어렵고, **실험 전에 표본 크기를 계산**해야 합니다.

### 5.4 흔한 실수와 함정

- **Peeking (중간 확인)**: 실험 도중 결과를 계속 보다가 유의하게 나온 순간 멈추면 **거짓 양성이 크게 늘어납니다.** 5% 위험의 "뽑기"를 여러 번 하는 셈이기 때문입니다. 실험 전에 정한 기간·표본이 찰 때까지 기다리는 것이 원칙입니다.
- **SRM (Sample Ratio Mismatch)**: 5:5로 배정했는데 실제로 10,000명 대 9,600명처럼 **비율이 어긋나면**, 우연으로 보기 어렵고 실험 결과 전체를 신뢰할 수 없습니다. 원인은 배정 로직 버그, 특정 그룹의 이벤트 유실, 봇 필터링 차이 등 대부분 **로깅·시스템 문제**입니다. 그래서 이 문제는 Growth Engineer의 영역입니다.
- **Guardrail 지표**: 주 지표(예: 결제 전환율)가 올라도 **악화되면 안 되는 보조 지표**(예: 결제 오류율, 이탈률, 페이지 로딩 시간)를 함께 봅니다.
- **통계적 유의성 ≠ 실무적 가치**: 표본이 매우 크면 0.01%p 차이도 유의하게 나옵니다. 효과 크기가 비용을 정당화하는지 따로 봐야 합니다.
- 주간 패턴이 있으므로 **최소 1~2주** 돌리고, 새 UI라서 초반에만 반응이 좋은 **신기 효과**도 고려합니다.

### 5.4 로깅과의 연결

- **노출(exposure) 이벤트**: "이 유저가 어느 버전을 실제로 보았는가"를 기록해야 분석할 수 있습니다. 배정만 하고 노출을 못 남기면 분석이 불가능합니다.
- 실험 플랫폼(Optimizely, Statsig, GrowthBook, Amplitude Experiment 등)을 쓰더라도, **이벤트 정합성과 SRM 진단**은 엔지니어가 책임집니다.

## 7. AI 에이전트 연동

공고의 "AI 에이전트 연동"은 **에이전트(SEO, CRM 등)가 정제된 데이터를 읽고 그에 따라 동작하도록** 데이터 접근 경로(테이블, API)를 만들어 주는 일입니다. 예를 들어 CRM 에이전트가 "최근 7일간 장바구니만 담고 이탈한 세그먼트"를 조회해서 메시지 캠페인 초안을 만드는 식입니다. 에이전트는 입력 데이터가 틀리면 **틀린 실행을 자동으로 대량 반복**하기 때문에, 데이터 품질의 중요도가 더 커집니다.
