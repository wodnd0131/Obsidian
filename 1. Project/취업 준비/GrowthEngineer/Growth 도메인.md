## Growth란?

Growth는 **제품이나 서비스의 성장(유저 확보·활성화·유지·매출)을 데이터와 실험으로 반복 개선하는 방식이자 직무 영역**입니다. 전통 마케팅이 "캠페인을 집행해 인지도를 높인다"에 가깝다면, Growth는 **"가설 → 실험 → 측정 → 학습"의 루프를 빠르게 돌려 성장 지표를 직접 움직인다**는 점이 다릅니다.

## 핵심 프레임워크: AARRR (Pirate Metrics)

| 단계          | 의미      | 대표 지표              |
| ----------- | ------- | ------------------ |
| Acquisition | 유입      | CAC, 채널별 유입량       |
| Activation  | 첫 가치 경험 | 가입 완료율, 온보딩 완료율    |
| Retention   | 재방문·유지  | D1/D7/D30 리텐션, 이탈률 |
| Revenue     | 수익화     | ARPU, LTV, ROAS    |
| Referral    | 추천·확산   | 바이럴 계수             |

Growth 팀은 이 퍼널에서 병목 구간을 찾아 개선합니다.

## 구성 요소

1. **측정**: 이벤트 로깅, 트래킹 (GA4, Amplitude, Mixpanel)
2. **분석**: 퍼널·코호트·세그먼트 분석
3. **실험**: A/B 테스트, 통계적 유의성 검증
4. **실행**: CRM/메시징(Braze), 광고, 프로덕트 개선
5. **자동화**: 반복 실행을 시스템·에이전트로 대체

## Growth Engineer의 위치

Growth 직군은 크게 Growth Marketer, Growth PM, Growth Analyst, **Growth Engineer**로 나뉩니다. Growth Engineer는 이 중 **측정과 자동화 기반을 구축하는 역할**입니다.

- 이벤트 스키마 설계와 SDK/태깅 구현으로 **"무엇을 어떻게 수집할지"** 결정
- ETL/ELT 파이프라인(Airflow, Kafka)으로 **데이터를 분석 가능한 상태로 가공**
- 데이터 품질 모니터링으로 **의사결정의 신뢰성 보장**
- 마케팅 툴·AI 에이전트와 데이터를 연결해 **실행 자동화**

일반 백엔드/데이터 엔지니어링과의 차이는 **산출물의 소비자가 마케터·PM이며, 성과 기준이 비즈니스 지표(CAC, ROAS, 전환율)** 라는 점입니다. 시스템 안정성뿐 아니라 "이 데이터로 어떤 의사결정을 하는가"까지 이해해야 합니다.

## 공고에 대입하면

NNT의 Growth Engineer는 위 정의에서 **"측정 + 파이프라인 + 자동화"** 영역에 집중된 포지션입니다. 다음 단계로 필요한 스킬 갭 분석이나 각 주요 업무(이벤트 로깅, 파이프라인 등)의 상세 설명 중 원하는 쪽으로 이어가겠습니다.


---
그 관점이면 차이는 스택이 아니라 **"무엇이 일의 출발점이고 무엇이 성공 기준인가"** 에 있습니다.

## 백엔드 (API 서버 운영)

- **출발점**: 요구사항. 기획된 기능이 있고, 그것을 정확히 구현합니다.
- **산출물**: 동작하는 API와 그것을 떠받치는 인프라
- **성공 기준**: 요구사항대로 동작하는가, 유저 수(트래픽)를 견디는가, 장애 없이 도는가
- **데이터의 위치**: 서비스가 굴러가는 재료이자 부산물. 저장하고 조회하는 대상이지, 그 자체가 목적은 아닙니다.
- **인프라 사고방식**: "유저가 늘어도 응답이 느려지지 않게" (스케일링, 가용성, 비용 대비 성능)

## Growth Engineer

- **출발점**: 질문과 가설. "가입 후 이탈 구간이 어디인가", "이 캠페인이 실제로 전환을 만들었는가"처럼 답해야 할 질문이 먼저 있고, 그 답에 필요한 데이터를 거꾸로 설계합니다.
- **산출물**: 신뢰할 수 있는 데이터와, 그 데이터로 의사결정·실행이 돌아가는 환경
- **성공 기준**: 마케터·PM이 그 데이터로 결정을 내렸는가, 실험이 돌아갔는가, 지표가 움직였는가
- **데이터의 위치**: 제품 그 자체. 서비스는 데이터를 만들어내는 원천입니다.
- **인프라 사고방식**: "데이터가 빠지거나 틀리지 않게" (정합성, 적시성, 재처리 가능성)

## 핵심 뉘앙스 차이

|          | 백엔드                | Growth Engineer        |
| -------- | ------------------ | ---------------------- |
| 요구사항의 성격 | 명세된 기능 (What이 주어짐) | 비즈니스 질문 (What을 같이 정의)  |
| 규모의 기준   | 동시 유저 수            | 이벤트 양, 데이터 정확도         |
| 실패의 모습   | 500 에러, 장애 (눈에 보임) | 조용히 틀린 데이터 (눈에 안 보임)   |
| 일의 끝     | 배포되어 동작하면 끝        | 그 데이터로 의사결정이 일어나야 끝    |
| 협업 관계    | 기획자가 준 명세를 구현      | 마케터·PM과 함께 무엇을 측정할지 정함 |
|          |                    |                        |

## 가장 큰 사고 전환 두 가지

**1. 수동적 구현자에서 능동적 설계자로**  
백엔드에서는 요구사항이 위에서 내려오지만, Growth에서는 "이 목표를 검증하려면 어떤 이벤트를 어떤 단위로 남겨야 하나"를 엔지니어가 먼저 제안해야 합니다. 이벤트 설계가 잘못되면 나중에 어떤 분석도 못 하기 때문에, 구현보다 설계 단계의 비중이 큽니다.

**2. 눈에 보이는 실패에서 안 보이는 실패로**  
API 서버는 죽으면 바로 알지만, 트래킹 누락이나 중복 집계는 아무도 모른 채 잘못된 결정으로 이어집니다. 그래서 공고에 데이터 품질 모니터링이 별도 업무로 들어가 있는 것입니다.

## 정리

기존 경험은 "잘 만들어진 시스템을 안정적으로 굴리는" 역량이고, Growth Engineer는 여기에 **"그 시스템이 만들어내는 데이터로 비즈니스가 의사결정을 하게 만드는"** 역할이 얹어집니다. 인프라 구축 감각은 그대로 쓰이되, 그 인프라의 목적이 "유저를 견디는 것"에서 "데이터를 신뢰 가능하게 흘려보내는 것"으로 바뀌는 셈입니다.

## Growth Engineer가 다루는 지표는 두 층

**1층: 비즈니스 지표 (이해하고 측정 가능하게 만들어야 하는 대상)**

직접 올리는 게 아니라, **정확히 측정되도록 인프라를 만드는 것**이 엔지니어의 몫입니다.

|단계|지표|
|---|---|
|유입|CAC, 채널별 유입량, ROAS|
|활성화|가입 완료율, 온보딩 완료율, 전환율|
|유지|D1/D7/D30 리텐션, 이탈률|
|수익|ARPU, LTV|
|실험|실험군·대조군 지표 차이, 통계적 유의성|

**2층: 데이터 인프라 지표 (엔지니어 자신의 성과 기준)**

백엔드의 응답시간·에러율에 대응하는 지표입니다.

- **정확성**: 이벤트 누락률, 중복률, 필수 속성 null 비율
- **적시성**: 이벤트 발생부터 분석 가능해질 때까지의 지연
- **일관성**: 스키마 준수율, 소스 간 수치 불일치 (예: 서버 결제 이벤트 대 GA4 수치)
- **운영**: 파이프라인 성공률, 장애 감지·복구 시간, 재처리 가능 여부
- **활용도**: 마케터·PM이 셀프서비스로 데이터를 쓸 수 있는가

핵심은 1층이 "이 직무가 무엇을 위해 존재하는가", 2층이 "그래서 내가 무엇으로 평가받는가"라는 점입니다.

## 직무적 관심사 정리

**1. 무엇을 측정할 것인가 (설계)**

- 비즈니스 질문에서 거꾸로 이벤트를 정의합니다.
- 이벤트 명명 규칙, 속성 구조, 유저 식별(익명 ID와 로그인 ID 연결)을 표준화합니다.
- 너무 적으면 분석이 안 되고, 너무 많으면 유지보수와 품질 관리가 무너지므로 수집 범위의 균형이 핵심입니다.

**2. 데이터를 믿을 수 있는가 (품질)**

- 클라이언트는 유실이 잦고 서버는 정확하다는 점을 고려해 핵심 이벤트를 서버에서 남깁니다.
- 중복·지연 도착·스키마 변경에 견디고, 문제가 생겨도 재처리로 복구되는 구조를 만듭니다.
- 이상을 사람이 발견하기 전에 시스템이 먼저 감지합니다.

**3. 데이터가 쓰이는가 (활용)**

- 파이프라인을 만드는 데서 끝나지 않고, 대시보드·분석 툴에서 마케터·PM이 실제로 결정을 내리는 데 쓰이는지를 봅니다.
- 다른 직군의 언어(CAC, ROAS, 전환율)로 소통합니다.

**4. 반복 실행을 자동화할 수 있는가 (자동화)**

- 실험(A/B)이 쉽게 돌아가는 환경을 만듭니다.
- 데이터를 CRM·마케팅 툴·AI 에이전트에 연결해 사람이 하던 반복 작업을 대체합니다.

## 면접용 한 문장 정리

> "백엔드는 **기능이 정확하게 동작하도록** 만드는 일이라면, Growth Engineering은 **비즈니스 결정이 정확한 데이터 위에서 내려지도록** 만드는 일이라고 이해했습니다. 그래서 시스템 안정성뿐 아니라 데이터 정합성과 적시성, 그리고 그 데이터가 실제 의사결정에 쓰이는지가 성과 기준이 된다고 생각합니다."

이 정리를 바탕으로 이어서 내일 면접용 예상 질문과 답변 구조를 잡아볼 수 있습니다.
