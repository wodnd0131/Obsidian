#  1. 요구사항 인지
- 상황 
	   레거시 서버 관련 `중요 문서` 유실,
	   `100개`의 데이터 조각이 흩어져 있음,
	   서버와 `통신`을 통해 복구할 것.
- 미션
   1. 서버가 `메모리`에 들고 있는 0번부터 99번까지의 `문자열` 값 수집
   2. `순서`대로 `공백` 으로 연결해서 하나의 문장 만들기
   3. 서버에 제출하기
   4. `승인(FLAG)` 받아내기

- 실행
```
docker load -i chaos_server.tar.gz 
docker run --rm --init -p 8080:8080 chaos_server
```
- 알려진 API 정보
GET `/data?id={index}` (0 <= index <= 99)
POST `/finalize`
(Body:{"full_sentence": "..."})
** 숨겨진 엔드포인트 추가 존재, 서버 응답 관찰 필요.

- 보안 메커니즘
서버는 실행 시 `표준 출력(stdout)`으로 로그를 출력합니다.
너무 `빠르게` 요청하면 차단당할 수 있습니다.

- 데이터 무결성 (중요)
간혹 `오염된 데이터` 반환
응답에 포함된 checksum 필드는 해당 데이터(value)의 SHA-256 해시값(Hex) 중 앞 16글자
** 반드시 검증 후 수집

## 분석
Growth 엔지니어링 모집 공고 + 과제 내용을 토대로, 과제의 의도 분석
외부 Growth 스택과 연동할 때 벌어지는 일들을 시뮬레이션한 과제로 판단

- 서버가 불안정 (500, 연결 끊김) 
->서드파티 API 환경 고려, 재시도/백오프 없이 파이프가 필요

- 너무 빠르게 요청하면 차단 
-> rate limit 설정됨, 적응형 속도 조절 필요

- 오염된 데이터 + checksum 검증
-> 채용공고에 명시된 "데이터의 정합성과 누락, 이상 데이터를 실시간으로 탐지"를  구현하게 만든 것

- stdout 로그에 힌트 존재
-> 문서화 안 된 API 특성을 관찰/추론 능력 확인 (벤더 API 문서가 부실할 때 어떻게 할 것인가?)

- 재현 가능한 코드베이스 요구
-> 일회성 스크립트가 아니라 "파이프라인"으로 설계했는지 확인
### 평가 포인트 추정

1. **멱등성/재개 가능성** — 서버가 중간에 죽거나 프로세스가 죽어도, 이미 검증된 0~99번 데이터는 다시 안 받아오고 이어서 진행할 수 있는지 (상태 저장)
2. **데이터 품질 검증을 "당연히" 하는 습관** — checksum 검증 로직을 빼먹지 않는지, 검증 실패 시 폐기 후 재요청하는지
3. **관찰 기반 디버깅** — 로그와 응답 헤더/바디를 진짜로 읽고 숨겨진 엔드포인트를 찾아내는지 
4. **문서화/커뮤니케이션** — 채용공고에 "협업을 위한 커뮤니케이션 능력"이 명시돼 있어요. 분석 일지가 그 대체 지표. 막힌 부분, 시행착오, 가설-검증 과정을 얼마나 명료하게 서술하는지도 채점 대상일 가능성 높음
5. **엔지니어링 위생** — requirements.txt/uv.lock, 도커 생애주기 관리까지 요구한 건 "동작만 하면 끝"이 아니라 재현 가능한 결과물을 내놓는 습관을 보는 것
