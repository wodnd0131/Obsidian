## stdout (표준 출력)이 뭔지

프로그램이 실행되면서 결과물을 내보내는 통로 중 하나입니다. 유닉스/리눅스 계열 프로세스는 기본적으로 3개의 표준 입출력 스트림을 갖습니다.

|스트림|이름|용도|파일 디스크립터 번호|
|---|---|---|---|
|stdin|표준 입력|프로그램이 외부에서 값을 받는 통로 (키보드 입력, 파이프 등)|0|
|**stdout**|**표준 출력**|프로그램의 **정상적인 결과/로그**를 내보내는 통로 (터미널 화면에 보통 출력됨)|1|
|stderr|표준 에러|에러 메시지 전용 출력 통로 (stdout과 분리되어 있어 로그와 에러를 구분 가능)|2|

### 이 문제 맥락에서의 의미

문제에서 "서버는 stdout으로 로그를 출력한다"는 건, 서버 프로세스가 실행되면서 **콘솔 화면(터미널)에 실시간으로 로그를 뿌린다**는 뜻입니다. Docker로 실행했으니:

```bash
docker run --rm --init -p 8080:8080 chaos_server
```

이 명령을 실행한 터미널 창에 로그가 그대로 출력됩니다. 만약 백그라운드로 돌렸거나(`-d` 옵션) 로그를 놓쳤다면:

```bash
docker ps                  # 컨테이너 이름/ID 확인
docker logs <컨테이너ID>    # 지금까지 쌓인 stdout/stderr 로그 확인
docker logs -f <컨테이너ID> # 실시간으로 계속 추적(follow)
```

문제에서 "모든 해답은 서버의 로그와 HTTP 응답 메시지 내 포함"이라고 했으니, **HTTP 응답 바디만 보지 말고 `docker logs`로 서버가 stdout에 찍는 내용도 같이 관찰**하라는 힌트입니다. 힌트, 디버그 메시지, 숨겨진 엔드포인트 이름, rate-limit 안내 등이 여기 섞여 나올 가능성이 높습니다.

### 유사 개념 몇 가지

- **stderr와의 구분**: 둘 다 화면에 같이 보이지만 별개 스트림입니다. `docker logs`는 기본적으로 stdout+stderr 둘 다 보여줍니다.
- **리다이렉션**: `command > out.txt`는 stdout만 파일로, `command 2> err.txt`는 stderr만 파일로 보냅니다. `2>&1`은 stderr를 stdout으로 합치는 것.
- **파이프(`|`)**: 한 프로세스의 stdout을 다른 프로세스의 stdin으로 연결하는 것.
- **로깅 프레임워크와의 차이**: 애플리케이션에서 흔히 쓰는 `logger.info()` 같은 것도 내부적으로 결국 stdout(혹은 파일)으로 나가도록 설정되는 경우가 많습니다. Docker/쿠버네티스 환경에서는 "로그는 stdout으로 찍어라"가 표준 관행입니다 (컨테이너 오케스트레이터가 stdout을 수집해서 중앙 로그 시스템으로 보내기 때문).

## checksum 필드 (SHA-256 앞 16글자) 설명

### SHA-256이란

입력 데이터를 넣으면 항상 **256비트(32바이트) 길이의 고정된 해시값**을 뱉어내는 암호학적 해시 함수입니다. 특징:

- 같은 입력 → 항상 같은 출력 (결정적)
- 입력이 1비트만 달라져도 출력이 완전히 달라짐 (눈사태 효과)
- 출력에서 입력을 역산하는 게 사실상 불가능 (일방향성)
- 서로 다른 입력이 같은 출력을 내는 경우(충돌)를 찾는 게 극도로 어려움

즉 "이 데이터가 변조되지 않고 원본 그대로인가?"를 검증하는 용도로 널리 쓰입니다. 흔히 파일 다운로드 페이지에서 보는 `sha256sum` 값도 같은 원리입니다.

### Hex(16진수)란

SHA-256의 원래 출력은 바이트(0~255) 32개짜리 이진 데이터입니다. 사람이 읽고 텍스트로 옮기기 편하게 **16진수 문자열**로 표현하는데, 바이트 1개당 16진수 2글자가 필요하므로 전체는 `32바이트 × 2글자 = 64글자`짜리 문자열이 됩니다.

예:

```
"hello" → SHA-256 → 
2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
```

(총 64자)

### "앞 16글자"의 의미

문제에서 말하는 checksum은 이 64자 전체가 아니라 **맨 앞 16글자만 잘라서 사용**한다는 뜻입니다. 이건 흔히 "짧은 해시(short hash)" 또는 "truncated hash"라고 부르는 방식입니다 (git commit hash 앞 7자리만 보여주는 것과 같은 관례).

### 검증 절차 (의사코드)

```python
import hashlib

def verify(value: str, checksum: str) -> bool:
    full_hash = hashlib.sha256(value.encode()).hexdigest()  # 64자 hex 문자열
    expected = full_hash[:16]  # 앞 16글자만 추출
    return expected == checksum
```

즉 `/data?id={index}` 응답으로 받은 `value`와 `checksum`이 같이 왔을 때:

1. `value`를 UTF-8 인코딩
2. SHA-256 해시 계산 → 64자 hex 문자열
3. 앞 16자만 잘라서
4. 서버가 준 `checksum`과 일치하는지 비교
5. 불일치하면 → "오염된 데이터"이므로 해당 인덱스를 재요청(retry)해야 함

### 참고로 알아두면 좋은 것

- `value` 앞뒤 공백이나 인코딩(UTF-8 vs 다른 인코딩)에 따라 해시값이 달라질 수 있으니, JSON 파싱 후 원본 문자열 그대로 넣었는지 주의가 필요합니다.
- Python이라면 `hashlib.sha256(value.encode('utf-8')).hexdigest()[:16]`가 표준적인 구현입니다.

## `.tar.gz`는 압축 방식 2단계가 합쳐진 확장자입니다

### 1. `.tar` — 묶기 (아카이빙)

**Tape ARchive**의 약자. 여러 파일/디렉토리를 **하나의 파일로 묶기만** 하는 포맷입니다. 압축은 하지 않습니다. 즉 파일 크기는 원본들을 그냥 이어붙인 정도로, 거의 줄어들지 않습니다.

- 비유: 박스에 여러 물건을 그냥 순서대로 담기만 한 것

### 2. `.gz` — 압축

**gzip** 압축 알고리즘으로 실제 용량을 줄이는 단계입니다.

- 비유: 그 박스를 진공팩으로 눌러서 부피를 줄이는 것

### 합치면 `.tar.gz`

"여러 파일을 하나로 묶은 뒤(tar) → 그걸 gzip으로 압축(gz)"한 결과물입니다. 리눅스/유닉스 생태계에서 가장 흔한 배포 포맷이고, `.tgz`로도 줄여 씁니다 (`.tar.gz`와 완전히 동일).

## Docker 이미지에서 이 확장자를 쓰는 이유

질문에 나온 `chaos_server.tar.gz`는 `docker save`로 만든 이미지 아카이브일 가능성이 높습니다:

```bash
docker save chaos_server:latest | gzip > chaos_server.tar.gz
# 또는
docker save -o chaos_server.tar chaos_server:latest && gzip chaos_server.tar
```

이걸 다시 불러올 때 `docker load -i chaos_server.tar.gz`로 압축을 자동 해제하면서 이미지로 복원합니다. 즉 `docker load`가 gzip 압축 해제 + tar 아카이브 풀기를 내부적으로 알아서 처리해줍니다.

## Windows에서 내용물 확인하고 싶다면

```powershell
# tar가 Windows 10/11에 기본 내장되어 있음
tar -tzvf chaos_server.tar.gz    # 내용물 목록만 보기 (풀지 않음)
tar -xzvf chaos_server.tar.gz    # 실제로 압축 해제
```

옵션 의미: `-x`(추출) `-t`(목록보기) `-z`(gzip 처리) `-v`(진행상황 출력) `-f`(파일 지정)

## 유사 확장자 비교

|확장자|묶기|압축 알고리즘|특징|
|---|---|---|---|
|`.tar`|O|없음|압축 안 됨|
|`.tar.gz` / `.tgz`|O|gzip|가장 흔함, 빠름|
|`.tar.bz2`|O|bzip2|gzip보다 압축률 높지만 느림|
|`.tar.xz`|O|xz(LZMA2)|압축률 최상, 더 느림|
|`.zip`|O+압축 동시|deflate|Windows에서 흔함, tar와 달리 묶기+압축이 한 단계|

tar 계열은 "묶기"와 "압축"이 분리된 두 단계라서 조합을 자유롭게 바꿀 수 있다는 게 zip과의 큰 차이입니다.


## 1. `docker load -i chaos_server.tar.gz`

**의미**: `.tar.gz`로 압축된 Docker 이미지 아카이브를 로컬 Docker에 불러와서(import) 사용 가능한 이미지로 등록하는 명령입니다.

|부분|설명|
|---|---|
|`docker load`|tar 아카이브 형태로 저장된 이미지를 Docker에 로드|
|`-i chaos_server.tar.gz`|`--input`의 축약형, 입력 파일 경로 지정|

앞서 설명드린 대로 `.tar.gz`는 gzip 압축된 tar 아카이브인데, `docker load`는 압축 해제까지 알아서 처리해줍니다. 실행하면 이 아카이브 안에 저장되어 있던 이미지가 `docker images` 목록에 `chaos_server`라는 이름(태그)으로 등록됩니다.

확인해보려면:

```powershell
docker images
```

목록에 `chaos_server` (또는 `chaos_server:latest`)가 보이면 성공입니다.

## 2. `docker run --rm --init -p 8080:8080 chaos_server`

**의미**: 방금 로드한 `chaos_server` 이미지로 실제 컨테이너를 띄워서 실행하는 명령입니다.

| 옵션             | 설명                                                                                          |
| -------------- | ------------------------------------------------------------------------------------------- |
| `docker run`   | 이미지로부터 새 컨테이너를 생성하고 실행                                                                      |
| `--rm`         | 컨테이너가 종료되면 자동으로 컨테이너를 삭제(정리). 디스크에 안 남기고 깔끔하게 테스트할 때 흔히 씀                                   |
| `--init`       | 컨테이너 안에 작은 init 프로세스(tini)를 PID 1로 끼워 넣음. 좀비 프로세스 정리, `Ctrl+C`(SIGINT) 같은 신호 처리를 제대로 해주기 위함 |
| `-p 8080:8080` | 포트 포워딩. `호스트포트:컨테이너포트` 형식. 즉 내 PC의 8080번 포트로 들어온 요청을 컨테이너 내부의 8080번 포트로 전달                  |
| `chaos_server` | 실행할 이미지 이름 (태그 생략 시 기본 `latest`)                                                            |

즉 이 명령을 실행하면:

1. `chaos_server` 이미지로 컨테이너가 뜨고
2. 컨테이너 내부에서 8080 포트로 서버가 리스닝 중이면
3. 내 컴퓨터에서 `http://localhost:8080`으로 접근 가능해집니다

### `--init`이 왜 중요한지 (보충)

컨테이너 안 애플리케이션이 직접 PID 1로 실행되면, 시그널 처리나 자식 프로세스 정리가 제대로 안 되는 경우가 있습니다(리눅스 프로세스 모델 특성). `--init`을 붙이면 tini라는 아주 가벼운 init 시스템이 PID 1 역할을 대신 맡아서, `Ctrl+C`로 컨테이너를 깔끔하게 종료하거나 내부적으로 생기는 좀비 프로세스를 정리해줍니다. 문제 설명에 "서버가 불안정하다"는 언급이 있으니, 이 옵션이 실행 안정성에 도움이 될 수 있습니다.

### 실행 후 확인

```powershell
# 다른 터미널 창에서
docker ps                    # 실행 중인지 확인
curl http://localhost:8080/data?id=0   # API 테스트
```

`--rm` 때문에 컨테이너를 중지하면(`Ctrl+C`) 바로 사라지니, 로그를 나중에 다시 보고 싶으면 그 창을 닫지 말고 계속 띄워두시거나, `docker logs`로 확인 가능한 별도 창에서 백그라운드(`-d`) 실행을 고려하셔도 됩니다.
