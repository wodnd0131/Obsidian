
신입 백엔드 이력서를 만들고 고칠 때 쓰는 기준, 구조, 문장 규칙, 검증 절차, 프롬프트를 정리한 문서입니다. 2026년 10월 이력서 개편 작업에서 확정한 내용을 기준으로 합니다. 포트폴리오·자기소개서는 이 이력서를 기준 문서로 삼습니다.

## 1. 원칙

- **이력서는 훑어 보는 문서입니다.** 문제 하나는 한 줄로 끝내고, 과정은 포트폴리오로 넘깁니다.
- **사실만 씁니다.** 구현하지 않은 기능, 측정하지 않은 수치, 지금 동작하지 않는 기능은 넣지 않습니다. "어렵지 않아서 한 것으로 친다"는 허용하지 않습니다.
- **모든 줄은 면접에서 방어할 수 있어야 합니다.** "PR 보여 주세요", "왜 그 값이죠?"에 답할 수 없는 줄은 낮추거나 뺀니다.
- **희소한 경험을 앞에 둡니다.** 이름을 가려도 다른 지원자와 구분되는 줄이 평가자의 눈에 먼저 들어와야 합니다.
- **한계는 숨기지 않되 이력서에는 쓰지 않습니다.** 한계는 포트폴리오와 면접 답변으로 준비합니다.

## 2. 근거 우선순위

이력서를 쓸 때는 아래 순서로 근거를 확인합니다. 이력서가 확정된 뒤에는 이력서가 다른 문서의 기준이 됩니다.

|   |   |   |
|---|---|---|
|순위|근거|비고|
|1|본인 진술 + PR·커밋·이슈·리뷰|페어 프로그래밍은 커밋 명의로 기여를 판단하지 않음|
|2|측정 기록(부하 테스트 결과, 대시보드, 콘솔 설정)|저장소 밖 설정은 캡처로 남김|
|3|기존 포트폴리오·자기소개서|수치가 문서마다 다르면 반드시 하나로 맞춤|
|4|팀원 자료|맥락 보충용. 팀원의 회고·성과를 본인 것으로 쓰지 않음|

## 3. 섹션 구조

2장 이내. 섹션 이름과 내용이 일치해야 합니다.

|   |   |   |
|---|---|---|
|순서|섹션|규칙|
|1|헤더|이름, 직무, GitHub·Blog·Portfolio·E-mail 링크|
|2|Introduce|헤드라인 1줄 + 근거 2문장 + 마무리 1문장|
|3|Skills.|분류별 나열, 버전 표기. 프로젝트에서 쓴 것만|
|4|Projects.|프로젝트 3개. 대표 프로젝트를 먼저|
|5|Education & Activities.|학교, 교육 과정, 활동. 활동마다 본인 행동 1~2줄|
|6|Awards & Certifications.|최신순. 수상과 자격증을 같은 형식(연도 + 명칭)으로|

## 4. Introduce

- **헤드라인:** 본인의 일하는 방식 한 줄. 본문 사례로 증명되는 주장만 씁니다.
- **근거 2문장:** 수치 하나 + 추적 경험 하나. 가능하면 서로 다른 프로젝트에서 가져와 한 번의 경험이 아니라 반복된 방식임을 보입니다.
- **마무리:** 행동과 그 효과를 구체적으로. "팀과 함께 나아갑니다" 같은 추상적 문장은 피합니다.
- 흔한 경험(예: 로그인 구현)은 Introduce에 올리지 않습니다.

예시(현재 확정본):

> **측정으로 원인을 좁히고, 판단 근거를 남기는 백엔드 개발자입니다.** 운영 중 DoS 공격을 같은 부하로 재현해 병목을 좁혀 p99를 79.7% 줄였고, 원인 불명의 409 오류를 추적하다 새 이미지가 삭제 예약되던 잠복 버그를 찾아냈습니다. 설계를 바꿀 때는 대안을 비교한 근거를 PR과 문서로 남겨, 다음 사람이 같은 고민을 반복하지 않게 합니다.

## 5. Projects

### 메타 줄 (2줄)

- 1줄: 프로젝트명 · 기간 · 한 줄 소개
- 2줄: 소속(팀 프로젝트/동아리/사이드 프로젝트) · 팀 구성 · 역할 · 기술 스택
- 기간은 저장소 활동 기간 기준. 문서마다 다르면 하나로 맞춥니다.

### 항목 줄

형식: `[태그] 문제 → 해결 → 결과(수치)`

- 태그는 내용을 부르는 짧은 이름(예: [성능], [하위 호환 고려], [신고·차단]). 포트폴리오도 같은 이름을 씁니다.
- 하위 목록 없이 줄글 한 문장. 길어도 두 줄.
- 문제 정의에는 왜 문제였는지가, 해결에는 배제한 대안이나 판단 근거가 보여야 합니다.
- 결과는 처음 문제에 대한 답입니다. 부차적 성과만으로 끝내지 않습니다.

### 줄 수와 정렬

- 대표 프로젝트 8줄 안팎, 나머지 4~7줄.
- 정렬 기준: 희소성 > 실제 운영 영향 > 인과 사슬의 완결성 > 직무 관련성.
- 문제 해결과 기본기(인프라·배포·협업)를 함께 두되, 기본기도 "혼자 배포까지 할 수 있는가"에 답하는 수준으로 남깁니다.
- 같은 기술 패턴(커서 페이징, Blue-Green 등)이 여러 프로젝트에 나오면 근거가 강한 쪽 하나만 남기거나, 두 번째는 다른 점만 짧게 씁니다.
- 하나의 인과 사슬(예: 알림으로 인지 → 재현 → 튜닝)이 두 줄로 쪼개지지 않게 합니다.

## 6. 문장 규칙

- 수치는 같은 지표끼리 비교합니다. (개선 전 P99와 개선 후 평균을 섞지 않음)
- 측정 조건을 괄호로 밝힙니다. (예: “15.2MB 원본, 로컬 Lambda 환경 실측”, “JMeter”)
- 과장 단어를 쓰지 않습니다. “통일”, “차단”, “완성”, “만료 표시”, “주도”는 코드가 정말 그렇게 동작할 때만.
- 역할 표기는 본인이 “팀원이 구현했다”고 한 부분에만 씁니다(예: SSE는 “제안·설계”). 페어 작업은 별도 표기하지 않습니다.
- 면접 질문을 부르는 단어를 점검합니다. (예: Replica를 쓰면 “읽기 라우팅은?”, “공격”을 쓰면 “어떻게 막았나?”)
- 운영 규모 숫자가 작으면(예: 50 이하) 쓰지 않습니다.
- 표기 통일: “우아한테크코스” 공식 명칭, “프론트” 하나로, 섹션 이름 끝 마침표 통일.

## 7. 넣지 않는 것

|   |   |
|---|---|
|유형|예|
|구현하지 않은 것|계획만 한 로그 수집 확장|
|지금 동작하지 않는 것|머지 후 롤백된 기능, 머지되지 않은 PR|
|근거를 찾지 못한 수치|출처가 없는 “약 82% 절감”|
|코드와 반대로 동작하는 설명|“로그아웃 시 재발급 차단”(실제로는 통과)|
|다른 사람의 결과물|팀원이 단독 구축한 파이프라인, 팀원의 회고|
|흔하고 약한 줄|결과가 “수정했다”뿐인 버그 수정|

## 8. 검증 절차

1. **근거 수집:** Claude Code로 저장소마다 커밋·PR(작성·어사인·리뷰)·이슈를 모아 작업 카드를 만듭니다. 식별자는 wodnd0131, 황재웅, wddy2001.
2. **주장 검증:** 이력서 문장을 구절마다 확인됨 / 부분 확인 / 근거 없음 / 반대 근거로 판정합니다.
3. **저장소 밖 근거:** AWS 콘솔 설정, 대시보드, 별도 저장소(부하 테스트, 설정, Lambda)를 따로 확인하고 캡처합니다.
4. **문서 간 대조:** 이력서·포트폴리오·자기소개서·팀원 자료의 기간, 수치, 표현을 맞춥니다.
5. **평가자 검토:** 아래 체크리스트로 점검합니다.

### 평가자 체크리스트

- 이름을 가려도 구분되는 줄이 첫 화면에 있는가
- 모든 줄이 문제 → 해결 → 결과 구조인가
- 같은 이야기가 두 번 나오지 않는가
- 메타 줄만 보고 역할과 범위를 알 수 있는가
- 면접에서 답하기 어려운 구절이 없는가

## 9. 재사용 프롬프트

```text
# 역할
너는 백엔드 신입 이력서를 함께 쓰는 첨삭 파트너다. 목표는 사실에 근거하면서 평가자가 읽고 싶어지는 이력서다. 통과를 위해 사실을 지어내지 않는다.

# 입력
- 현재 이력서: {붙여넣기}
- 저장소 근거: {resume-evidence/*.md}
- 참고 자료: {기존 포트폴리오, 자기소개서, 팀원 자료}

# 사실 규칙
- 구현하지 않은 기능, 측정하지 않은 수치, 지금 동작하지 않는 기능은 쓰지 않는다. 내가 요청해도 쓰지 않고, 사실만으로 가장 강한 표현을 찾는다.
- 추정한 내용은 [검토: …], 받지 못한 사실은 [빈칸: …]으로 표시한다.
- 문서 간 표현이나 수치가 다르면 반드시 짚는다.
- 페어 작업이 많으므로 커밋 명의로 기여를 판단하지 않는다. 내가 팀원 구현이라고 한 부분만 역할을 표기한다.

# 형식
- 섹션: 헤더 / Introduce / Skills. / Projects. / Education &amp; Activities. / Awards &amp; Certifications. (2장 이내)
- Introduce: 헤드라인 1줄 + 수치 하나와 추적 경험 하나(가능하면 다른 프로젝트) + 구체적인 마무리 1문장
- 프로젝트 메타 2줄: 이름 · 기간 · 한 줄 소개 / 소속 · 팀 구성 · 역할 · 스택
- 항목: [태그] 문제 → 해결 → 결과(수치), 하위 목록 없이 한 문장
- 정렬: 희소성 > 운영 영향 > 인과 완결성 > 직무 관련성. 대표 프로젝트 8줄 안팎

# 작업 순서
1. 현재 이력서 진단 (구조, 중복, 기본기와 강점의 비율)
2. 항목별 수정안: 본문 → 바꾼 점 → 확인할 것
3. 평가자 시점 비판 (면접 예상 질문, 방어하기 어려운 구절)
4. 문서는 내가 요청할 때만 만들거나 고친다.
```
