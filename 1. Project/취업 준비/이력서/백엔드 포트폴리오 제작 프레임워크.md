
이력서를 바탕으로 슬라이드형 포트폴리오를 만들 때 쓰는 기준, 구조, 형식, 프롬프트를 정리한 문서입니다. 2026년 10월 초본 작업에서 확정한 내용을 기준으로 합니다.

## 1. 원칙

- **이력서가 최우선 기준입니다.** 자료가 서로 다르면 이력서 > PR·커밋·저장소 기록 > 기존 포트폴리오 > 팀원 자료 > 대화 중 기억 순으로 따릅니다. 수치와 표현은 이력서와 글자 하나까지 맞춥니다.
- **포트폴리오는 사고의 흐름을 보여 주는 문서입니다.** 무엇을 관찰했고, 무엇을 배제했고, 왜 그 방법을 골랐는지가 핵심입니다. 기술 이름 나열은 장점이 아닙니다.
- **두괄식으로 보여 줍니다.** 사례마다 그림과 요약을 먼저, 글을 나중에 둡니다.
- **가독성이 제1순위입니다.** 제목과 라벨은 줄바꿈이 없어야 하고, 글을 카드에 세로로 가두지 않습니다.
- **사실만 씁니다.** 구현하지 않은 기능, 측정하지 않은 수치는 넣지 않고, 빈 곳은 [~ 필요]로 남깁니다. 한계는 먼저 밝힙니다.

## 2. 주제 선정 기준

이력서의 모든 항목을 다루지 않습니다. **포트폴리오가 있어야 설명되는 주제**를 고릅니다.

|        |                                                 |                                            |
| ------ | ----------------------------------------------- | ------------------------------------------ |
| 기준     | 남길 주제                                           | 빼는 주제                                      |
| 희소성    | 다른 지원자가 쓸 수 없는 경험 (운영 중 API 전환, 라이브러리 스펙 변경 추적) | 흔한 패턴 (N+1, 커서 페이징, UNIQUE 기반 멱등성, 비동기 분리) |
| 설명의 깊이 | 대안 비교와 판단 과정이 있는 것                              | 구현만 있고 판단이 없는 것                            |
| 근거     | 그림·측정·PR로 보여 줄 수 있는 것                           | 저장소에서 확인되지 않는 것                            |
|        |                                                 |                                            |

- 프로젝트당 2~4개 사례. 대표 프로젝트에 비중을 둡니다.
- 사례 이름은 이력서 태그와 같게 부릅니다. (예: 이력서 [생성 지연] → 포트폴리오도 "생성 지연")
- 선정 후 이력서 ↔ 포트폴리오 대조표를 만들어 빠진 항목과 이름 불일치를 확인합니다.

|3|프로젝트 소개·아키텍처|서비스 화면, 아키텍처 다이어그램 (그림 장)|

|7|부록|부록 목차 + 보조 그림·캡처|

## 4. 사례 템플릿

**핵심 사례 (3~4장):** 대표 그림 + 요약 → 문제 정의·시도·결과 (1~2장) → 근거 (표·수치·한계)

**보조 사례 (2장):** 그림 + 요약 → 문제 정의·시도·결과

보조 그림(대시보드 캡처, 콘솔 설정, 타임라인)은 본문에 넣지 않고 부록으로 보냅니다. 근거 장 하단에 "부록 A-n (n쪽)", 부록 장 하단에 "관련 본문 (n쪽)"을 적어 서로 찾아갈 수 있게 합니다.

## 5. 장 유형별 형식

### 그림 장

- 상단: 태그(프로젝트 · 주제) + 제목(그림이 무엇인지)
- 가운데: 가로로 넓은 이미지 1개, 슬라이드 폭 전체. 여러 장을 카드로 나란히 두지 않습니다.
- 하단: "요약" 상자. 이력서 문장을 그대로 넣습니다.

### 흐름 장 (문제 정의 → 시도 → 결과)

- 문서처럼 위에서 아래로 쌓습니다. 왼쪽에 색 있는 단계 이름, 오른쪽에 슬라이드 폭 거의 전체를 쓰는 항목 목록. 구역 사이는 가는 선만 씁니다.
- 카드 3열 형식은 쓰지 않습니다. (글이 세로로 갇혀 읽기 어렵습니다)
- 구역당 2~4항목, 항목은 한두 줄. "무엇을 확인해서 무엇을 배제했는지"가 보이게 씁니다.
- 결과는 처음 문제에 대한 답이어야 합니다. 핵심 수치는 굵게.

### 근거 장

- 표(대안 비교, 단계별 측정)를 슬라이드 폭 전체로.
- 큰 수치 카드 2~3개.
- "한계와 다음 단계" 상자를 반드시 둡니다.
- 하단에 부록 참조와 근거 링크.

### 기타

- **개요:** 사례 이름 옆에 시작 쪽(p.n). 슬라이드 간 하이퍼링크는 지원되지 않으므로 쪽 번호로 연결합니다. 필요하면 PowerPoint로 내려받아 슬라이드 링크를 겁니다.
- **협업:** 3칸 코디네이트 카드 허용(글이 짧아서 예외).
- **마무리:** 어두운 배경, "감사합니다", GitHub·블로그·이메일, 부록 시작 쪽.

## 6. 문장 규칙

- 제목은 한 줄(25자 안팎), 개요의 사례 이름은 12자 안팎.
- "사례 1" 같은 번호 표현은 쓰지 않고 "프로젝트 · 주제" 태그만 씁니다.
- 제목은 사실을 담담하게(예: "장애 상황을 메트릭으로 해부하다"). 연설조·비유는 피합니다.
- 팀원 구현은 역할을 밝힙니다(예: SSE는 "제안·설계").
- 빈 곳 표시: [이미지 필요: …], [측정 필요: …], [필요: …], [확인 필요: …], [링크 필요].

## 8. 작업 순서

1. 이력서를 먼저 확정합니다.
2. Claude Code로 프로젝트별 저장소 근거를 모읍니다(커밋·PR·이슈·리뷰, 주장 검증표).
3. 기존 포트폴리오·팀원 자료에서 수치와 맥락을 보충하되, 이력서와 다르면 짚고 이력서를 따릅니다.
4. 이력서 ↔ 포트폴리오 대조표로 주제를 선정합니다.
5. 초본을 만들고 빈 곳을 [~ 필요]로 표시합니다.
6. 평가자 시점으로 검토하고 고칩니다. (면접에서 나올 질문, 문서 간 불일치)

```text
# 역할
너는 백엔드 신입 포트폴리오를 함께 만드는 편집자다. 사실에 근거하면서, 평가자가 짧은 시간에 판단 과정을 읽을 수 있는 슬라이드를 만든다.

# 입력
- 확정된 이력서: {붙여넣기}
- 저장소 근거 파일: {프로젝트별 resume-evidence/*.md}
- 참고 자료: {기존 포트폴리오, 팀원 자료, 다이어그램·캡처 이미지}

# 사실 규칙
- 우선순위: 이력서 > PR·커밋 > 기존 포트폴리오 > 팀원 자료 > 대화 기억.
- 자료끼리 다르면 짚고, 슬라이드에는 이력서 표현을 쓴다.
- 구현하지 않은 기능, 측정하지 않은 수치는 쓰지 않는다. 빈 곳은 [~ 필요]로 남긴다.
- 맥락으로 보강한 문장은 답변에서 따로 알린다.

# 주제 선정
- 이력서 항목 중 포트폴리오가 있어야 설명되는 것만 고른다. 희소한 경험, 대안 비교가 있는 판단을 우선하고 흔한 패턴은 뺀다.
- 프로젝트당 2~4개. 사례 이름은 이력서 태그와 같게 한다.
- 먼저 이력서 ↔ 포트폴리오 대조표를 보여 주고 선정 이유를 한 줄씩 적는다.

# 구조
표지 → 개요(사례별 시작 쪽) → 프로젝트별 [소개·아키텍처 → 사례들] → 협업 → 마무리(감사 인사) → 부록(목차 + 보조 그림)
- 핵심 사례: 그림 장(이미지 + 이력서 문장 요약) → 흐름 장 → 근거 장
- 보조 사례: 그림 장 → 흐름 장
- 보조 그림은 부록으로 보내고, 쪽 번호로 본문과 서로 연결한다.

# 형식
- 그림 장: 가로로 넓은 이미지 1개를 폭 전체로, 하단에 요약 상자. 카드로 여러 장 나란히 두지 않는다.
- 흐름 장: 문제 정의 / 시도 / 결과를 문서처럼 위에서 아래로. 왼쪽 단계 이름, 오른쪽 폭 전체 목록. 카드 3열 금지.
- 근거 장: 표를 폭 전체로, 큰 수치, 한계와 다음 단계, 부록 참조.
- 제목은 한 줄(25자 안팎), 라벨은 줄바꿈 없이. "사례 N" 표현 금지.
- 16:9, Noto Sans KR, 본문 26px, 가독성 우선.

# 출력
- 슬라이드 덱을 만들고, 답변에는 구성표, 채워야 할 [~ 필요] 목록(이미지/측정/답변/링크별), 문서 간 불일치를 적는다.
```
