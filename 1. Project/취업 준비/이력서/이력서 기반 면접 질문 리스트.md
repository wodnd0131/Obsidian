# Introduce

## 변경점

- 기존: "원인 재정의 + 가성비 기준점" 프레임 + 3개 사례 요약 (Projects와 중복)
- 변경: **"가장 작은 해법으로 풀고, 다음 단계로 넘어갈 기준을 함께 남깁니다"** 한 문장 프레임 + Matilda 단일 사례
- 사례 서사 구조: 증상 → 원인 → 해법 계열 결정(캐시) → **기본값 의심**(Redis가 푸는 문제가 환경에 실재하는가) → 선택 → 이관 기준

## 이야기할 수 있는 면접 대화 포인트

**Q. 자기소개 해주세요. / 본인을 한 문장으로 표현한다면?**

- 프레임 문장을 그대로 말한다: "가장 작은 해법으로 풀고, 다음 단계로 넘어갈 기준을 함께 남기는 개발자입니다."
- 이어서 Matilda 사례를 30초 버전으로: 증상(p99 1.42s) → 원인(정적 데이터 매 요청 DB 조회) → Redis 검토했으나 단일 인스턴스라 분산 캐시가 풀 문제가 없음 → JVM 캐시 선택 → Redis 도입 기준을 문서로 남김

**Q. "가장 작은 해법"이 뭔가요? 그냥 대충 하는 거랑 뭐가 달라요?**

- 핵심 구분: 작은 해법 ≠ 임시방편. **성립 조건을 확인하고 고른 해법 + 조건이 깨질 때의 이관 기준**이 세트다.
- 임시방편은 조건 확인도, 이관 기준도 없다. 나는 둘 다 남긴다.
- 예: JVM 캐시는 "단일 인스턴스"라는 조건 위에서만 성립. 그래서 "다중 인스턴스 전환 시점 = Redis 도입 시점"을 기준으로 문서화했다.

**Q. 반대로, 큰 해법이 처음부터 필요했던 적은 없나요?**

- Orbits 미아 객체 사례로 답변 가능: 애플리케이션 레벨 정리 배치(작은 해법처럼 보임)를 선택하지 않고 인프라 레벨(S3 Lifecycle)로 간 이유 → 배치는 "작아 보이지만" 운영 개입·실패 처리·재시도 로직이 계속 붙는 해법. 총 소유 비용 기준으로는 인프라 위임이 더 작았다.
- 포인트: "작음"의 기준은 코드량이 아니라 **총 소유 비용(운영 포함)**.

## 매력적인 포인트와 올바른 답변 방향

- **매력**: 신입/주니어 대부분은 "뭘 썼다"를 말한다. 이 프레임은 "뭘 안 썼고 왜 안 썼는지 + 언제 쓸 건지"를 말한다. 기술 선택에 대한 메타 인지가 있다는 신호.
- **주의**: 프레임 문장이 입에서 자연스럽게 나올 때까지 소리 내서 연습할 것. 글로만 멋진 문장은 첫 질문에서 무너진다.
- **함정 회피**: "그럼 Redis 못 쓰는 거 아니에요?"류 질문에는 "안 쓴 게 아니라 도입 시점을 정의한 것"으로 즉시 재프레임. 기술 회피가 아니라 도입 기준 설계임을 강조.

# Pickeat — DoS 대응을 통한 추적 체계 구축 및 성능 개선

## 변경점

- "비정형 로그와 메트릭" → "비정형 로그로는 원인 특정 불가"로 문제 정의 명확화
- k6 재현 조건을 실제 스크립트 기반으로 확정: **실사용 전체 플로우 재현**(방 생성 → 식당 등록 → 참가자 10명 생성 → 조회/소거/좋아요 → 결과 확정), `ramping-arrival-rate` executor로 **분당 5 → 50 → 100 → 200 → 250세션 램프업**(7분, maxVUs 500)
- **Rate Limiting은 이력서에서 완전히 제외** — 임계치 산정 근거가 없어 서면 주장으로는 리스크. 질문이 나오면 답변으로만 대응 (아래 Q 참조)
- "동일 부하 조건에서" p99 79.7% 개선 — 측정 조건 고정 명시

## 이야기할 수 있는 면접 대화 포인트

**Q. DoS 상황을 구체적으로 설명해주세요. 진짜 DoS였나요?**

- 정직하게: 외부 공격이 아니라 데모 중 트래픽 집중으로 인한 서비스 불능 상태였다면 그렇게 말한다. "DoS성 부하 상황"으로 표현 조정.
- 중요한 건 공격 여부가 아니라 **"병목은 보이는데 원인을 못 찾는 상태"를 어떻게 벗어났는가**로 대화를 끌고 가는 것.

**Q. k6로 어떻게 재현했어요? 그냥 API 반복 호출인가요?**

- **적극 어필 지점.** 단순 반복이 아니라 실사용 전체 플로우를 스크립트로 재현했다:
    - 방 생성 → 식당 등록 → 참가자 10명 생성 → 참가자별 조회 3회·소거·재조회 3회·좋아요 5회 → 결과 확정/비활성화/조회
    - 요청 간 랜덤 sleep(0.05~2s)으로 실제 사용자 행동 패턴 모사, 참가자 생성 간 지연으로 락 충돌 상황까지 재현
- 부하 방식: `ramping-arrival-rate` — VU 고정이 아니라 **도착률 기반**(분당 신규 세션 수)으로 5 → 250세션/분까지 7분 램프업, maxVUs 500
- 커스텀 메트릭(`pickeat_created/completed/failed`)으로 **HTTP 성공률이 아닌 비즈니스 플로우 완주율**을 측정 — 기술 지표와 비즈니스 지표를 구분했다는 신호
- 임계 조건: `http_req_failed < 5%`, `p(95) < 1500ms`, 완주 10건 이상

**Q. 왜 VU 고정이 아니라 arrival-rate 방식을 썼어요?**

- VU 고정(closed model)은 서버가 느려지면 요청 발생도 같이 느려져 부하가 자기 조절됨 → 실제 트래픽은 서버 상태와 무관하게 계속 유입됨(open model)
- DoS성 상황 재현이 목적이므로 서버 응답 지연과 무관하게 도착률을 유지하는 arrival-rate가 정확한 모델
- **이 답을 하면 부하 테스트 이해도가 한 급 올라간다. open/closed model 개념 숙지해둘 것.**

**Q. 로그를 "객체화"했다는 게 무슨 뜻이에요?**

- 답변 뼈대: 문자열 이어붙이기 로그 → 목적별 카테고리(요청/에러/외부호출 등)를 가진 구조화 객체로 정의 → JSON 직렬화 → 수집기에서 필드 단위 검색/집계 가능.
- 기술 키워드: MDC, Logstash Markers, 구조화 로깅(Structured Logging).
- 우테코 테크 세션 주제(관찰 가능성)와 연결하면 일관된 서사가 된다.

**Q. Trace ID는 어떻게 전파했어요?**

- MDC 기반이면: 필터에서 요청 진입 시 UUID 발급 → MDC 저장 → 로그 패턴에 포함 → 응답/에러까지 동일 ID로 추적.
- 비동기 구간(@Async, 이벤트)에서 MDC 유실 문제를 겪었다면 그 해결(TaskDecorator 등)까지 말하면 상급.
- **사전 확인 필요**: 실제 구현 범위가 어디까지였는지 코드 다시 볼 것. 안 한 걸 했다고 하면 꼬리 질문에서 무너진다.

**Q. Tomcat Thread / HikariCP를 어떻게 튜닝했어요? 근거는?**

- 답변 구조: ① idle 상태 baseline 측정 → ② k6 부하에서 스레드 대기/커넥션 대기 관찰 → ③ 병목 지점(스레드 고갈 vs 커넥션 고갈) 판별 → ④ 값 조정 후 재측정.
- 절대 피할 답: "적당히 올렸다", "일반적으로 쓰는 값으로 했다".
- 숫자 준비: before/after 스레드 수, 풀 사이즈, 그 값을 고른 계산 근거.

**Q. Rate Limiting 같은 유입 차단은 안 했어요?** (이력서에 없으므로 먼저 꺼내지 말 것)

- 이력서에서 뺀 이유가 그대로 답이 된다: "Nginx `limit_req`(leaky bucket)로 적용은 했지만, 당시 임계치가 정교한 근거 없이 보수적 추정으로 들어갔다. 근거 없는 숫자를 성과로 쓰고 싶지 않아 이력서에서는 제외했다."
- 이어서 개선 방향: "지금 다시 한다면 k6 시나리오의 정상 사용자 요청률(요청 간 sleep 포함, 대략 초당 1~2회)을 실측해 안전 마진 3~5배로 임계치를 역산하고, 정상 플로우가 차단되지 않는지 동일 스크립트로 검증했을 것."
- 이 답의 구조: 한 것 인정 → 근거 부족 인정 → 역산 방법론 제시. **"근거 없는 숫자는 성과에 안 쓴다"는 태도 자체가 이력서 전체 숫자의 신뢰도를 올려준다.**

**Q. p99 79.7%는 어떤 조건에서 측정했나요?**

- "동일 부하 조건" = 위 k6 스크립트 동일 시나리오·동일 램프업으로 before/after 비교.
- 즉답 스펙: "실사용 플로우 재현 스크립트, 분당 최대 250세션 도착률, maxVUs 500, 7분 램프업."

## 매력적인 포인트와 올바른 답변 방향

- **매력 1**: "튜닝했다"가 아니라 **"추적 가능한 상태를 먼저 만들고 나서 튜닝했다"**는 순서. 관찰 가능성 → 측정 → 개선의 정석 루프.
- **매력 2 (신규)**: 부하 테스트의 설계 수준 — ① 실사용 플로우 재현 ② open model(arrival-rate) 선택 ③ 비즈니스 완주율 커스텀 메트릭. 셋 다 "k6 돌려봤어요" 수준과 명확히 구분되는 지점이므로, 부하 테스트 질문이 오면 이 세 가지를 순서대로 꺼낼 것.
- **최대 약점**: 구축한 체계가 이후 실제로 뭔가를 잡아낸 사례가 없음(재발 감지 부재). 질문이 들어오면 — "이후 동일 수준 장애가 재발하지 않아 실전 검증 기회는 없었지만, 신규 기능 디버깅 시 Trace 기반 로그 검색으로 원인 파악 시간이 체감상 크게 줄었다" 수준으로 정직하게. 과장 금지.
- **연결 어필**: Observability 스킬(Grafana, Loki, Prometheus, Alloy)이 이 경험에서 나왔음을 언급하면 스킬 섹션이 장식이 아니게 된다.

# Pickeat — 폴링 → SSE 전환

## 변경점

- 기존 "1분 단위 폴링" → 실제 코드 확인 결과 **3초 폴링**으로 정정 (usePolling interval: 3000)
- 문제 정의 재구성: "요청 수가 활동량이 아닌 **세션 시간에 비례**하는 구조" → 의사결정이 길어질수록 유휴 구간 낭비 누적
- 시나리오 기준 산출값 명시: 7명·8분, 폴링 1,120회 → SSE 686회 (39% 감소)

## 이야기할 수 있는 면접 대화 포인트

**Q. 1,120회, 686회는 실측인가요?**

- 정직하게: **시나리오 기반 산출값**. 산출식을 바로 말한다.
    - 폴링: 7명 × (480초 ÷ 3초) = 1,120회
    - SSE: 변경 98건(인당 식당 등록 10 + 좋아요 4, × 7명) × 7명 재조회 = 686회
- "실측 로그가 남았다면 그걸 썼을 것"이라는 태도까지.

**Q. SSE 알림 받고 다시 fetch하는 구조면, 변경이 몰릴 때 오히려 스파이크 아니에요?**

- **이 질문은 반드시 나온다. 준비된 답이 있어야 한다.**
- 인정 + 다음 단계: "맞다. 변경마다 전원 재조회라 변경 밀도가 높으면 폴링보다 나빠질 수 있다. 개선 방향은 두 가지 — ① 알림에 델타 페이로드 포함(재조회 제거) ② 서버 측 디바운스(예: 1초 내 변경 묶어 1회 알림). 당시 규모에선 39% 감소로 충분했고, 이관 기준은 '변경 빈도가 폴링 주기 환산 요청량을 넘는 시점'."
- Introduce 프레임("다음 단계 기준을 남긴다")과 그대로 연결됨 — 의도적으로 연결해서 답할 것.

**Q. 세션이 짧으면 폴링이 더 나은 거 아니에요?**

- 맞다고 인정: 활동 밀도가 높고 짧은 세션에선 폴링이 유리할 수 있다.
- 우리 서비스 특성 근거: 유저가 가게 정보를 읽느라 idle 구간이 긴 서비스(실측: 7명이 8분 소요). 요청 수가 시간에 비례하는 폴링은 이 특성과 정면 충돌 → SSE가 맞았다.
- 포인트: 기술 우열이 아니라 **서비스의 트래픽 특성과 해법의 비례 축을 맞춘 것**.

**Q. WebSocket은 왜 안 썼어요?**

- 통신 방향성으로 답변: 서버→클라이언트 단방향 알림만 필요(투표 자체는 일반 HTTP POST). 양방향이 필요 없는데 WebSocket은 과한 해법.
- SSE 장점: HTTP 기반이라 인프라 변경 없음, 자동 재연결 내장.
- 이것도 "가장 작은 해법" 프레임의 사례로 연결 가능.

## 매력적인 포인트와 올바른 답변 방향

- **매력**: "폴링→SSE로 바꿨다"(기술 나열)가 아니라 **"요청 수의 비례 축을 시간에서 활동량으로 옮겼다"**(구조 인식)로 말하는 것. 이 한 문장이 급을 가른다.
- **주의**: 39%는 최악 가정(전원 재조회) 기준임을 알고 있을 것. 델타/디바운스를 이미 구현한 것처럼 말하지 말 것 — 개선 방향으로만.

# Pickeat — 단계적 삭제 파이프라인

## 변경점

- MySQL Event Scheduler 선택 이유 추가: "물리 삭제를 **애플리케이션 배포 주기와 분리**하기 위해 DB 레벨에서 수행"
- 실행 이력 로그 기록으로 가시성 확보 문구 추가
- 실측 숫자 명시: 운영 테이블(식당 정보) 4,780건 → 200건

## 이야기할 수 있는 면접 대화 포인트

**Q. MySQL Event Scheduler는 운영에서 잘 안 쓰는데, 왜 썼어요?**

- **가장 위험한 질문. 방어 논리를 정확히.**
- 인정할 것: Event Scheduler의 일반적 단점 — 실행 실패 가시성 부족, 로직이 DB에 숨음, 형상 관리 어려움.
- 선택 근거: ① 물리 삭제/아카이빙은 순수 데이터 작업으로 앱 로직 의존 없음 ② 앱 배포·재시작과 무관하게 동작해야 함 ③ 당시 별도 배치 인프라(스케줄러 서버) 없는 환경에서 가장 작은 해법.
- 보완: 실행 이력 로그 기록으로 가시성 확보.
- 이관 기준: "삭제 로직에 비즈니스 규칙이 붙는 시점(예: 조건부 보존), 또는 배치 인프라 도입 시점 → Spring Batch/스케줄러로 이관."

**Q. 왜 소프트딜리트를 먼저 하고 물리 삭제를 나중에 해요? 그냥 지우면 안 돼요?**

- 데이터 성격 구분: 복구 요청 가능 기간, 정산/통계 참조 기간 동안은 논리 삭제로 보존 → 기간 경과 후 아카이빙 이전 → 물리 삭제.
- 소프트딜리트만 쓰면: 운영 테이블 비대화, 모든 조회 쿼리에 `deleted = false` 조건 강제, 인덱스 효율 저하 → 그래서 "단계적".

**Q. 4,780 → 200건이면 크지 않은 규모인데, 이게 의미 있나요?**

- 정직 + 구조 강조: "규모 자체는 작다. 하지만 문제는 크기가 아니라 **증가 추세와 삭제 전략 부재**였다. 방치하면 조회 성능 저하가 예정된 구조였고, 자동 파이프라인을 만들어 사람 개입 없이 유지되게 했다는 게 핵심."
- 인덱스 효율 개선을 정량으로 물으면: 측정했으면 숫자, 안 했으면 "레코드 수 감소에 따른 이론적 개선이며 별도 측정은 하지 않았다"로 정직하게.

## 매력적인 포인트와 올바른 답변 방향

- **매력**: 데이터 생애주기(hot → soft-deleted → archived → purged)를 설계했다는 것. CRUD를 넘어 운영 관점이 있다는 신호.
- **주의**: Event Scheduler 방어가 준비 안 된 상태로 이 항목을 먼저 꺼내지 말 것. 면접관이 꺼내면 위의 방어 논리로.

**Q. After인데 Max가 985ms나 되는 이유는?**

- "동시 30명 순간 투입이라 초기 요청들이 캐시 적재 전에 DB를 때린 콜드 스타트 구간이 포함됐다. warm 상태에선 Min 89ms 수준."

**Q. 5분 주기 무효화면 5분간 stale 데이터인데 괜찮아요?**

- 태그 갱신 빈도가 낮아 5분 낭비가 무시 가능한 수준 → 가장 작은 해법.

**Q. 다중 인스턴스로 가면 어떻게 할 거예요?**

- 준비된 답: "각 인스턴스의 로컬 캐시가 서로 다른 시점 데이터를 갖는 정합성 문제가 실재하게 되는 시점 — 그게 문서로 남긴 Redis 도입 기준이다. 그때는 중앙 캐시 + pub/sub 무효화 or TTL 정책 재설계."
- Introduce와 동일 서사 — 일관성이 곧 신뢰.

**Q. 캐시 구현은 뭘로 했어요? (직접 구현? Caffeine? Spring @Cacheable?)**

- **사전 확인 필요**: 실제 구현 방식 코드 확인. ConcurrentHashMap 직접이면 동시성 처리(갱신 중 조회) 어떻게 했는지까지.

## 매력적인 포인트와 올바른 답변 방향

- **매력**: Redis라는 기본값 앞에서 멈추고 "이 기술이 푸는 문제가 우리 환경에 있는가"를 물은 것. + 처리량 2.6배 = 캐시가 응답속도만이 아니라 **DB 병목 해소로 시스템 수용량을 키웠다**는 증거.

# Orbits — Lambda 스트리밍 이미지 압축 파이프라인

## 변경점

- 82% 숫자의 정체 명시: **샘플 50장 실측, 원본 대비 용량** 절감 (비용 주장 → 용량 실측으로 정정)
- 원본 처리 정책 추가: **30일 후 Glacier Flexible Retrieval 이전** Lifecycle — 재처리 가능성 보존 + 보관 비용 최소화
- "스트리밍" 구체화: PassThrough 분기, 청크 단위 처리, 메모리 적재 최소화

## 이야기할 수 있는 면접 대화 포인트

**Q. 82%는 어떻게 측정한 숫자예요?**

- 한 문장: "업로드 분포를 반영한 샘플 50장으로 원본 대비 variant 용량을 실측한 값입니다."
- 꼬리(50장이 대표성 있나?): "프로필 이미지는 촬영 사진 위주로 포맷·해상도 분포가 좁아 50장으로 충분하다고 판단했고, 운영 데이터가 쌓이면 전수 집계로 교체할 계획." — 가장 작은 측정.

**Q. 원본은 왜 삭제 안 하고 Glacier로 보냈어요?**

- "variant 규격 추가·품질 정책 변경 시 원본에서 재생성해야 한다. 삭제하면 그 가능성이 죽는다. Glacier Flexible은 Standard 대비 보관비 약 1/6이고, 재처리는 급한 작업이 아니라 복원 대기시간(수 시간)이 허용된다."
- Instant vs Flexible 선택 근거까지 말하면 상급: 즉시 복원이 필요한 조건이 없으므로 더 싼 Flexible.

**Q. 왜 Lambda예요? 서버에서 처리하면 안 돼요?**

- 트래픽 특성: 이미지 업로드는 간헐적 버스트 → 상시 리소스 점유가 낭비. 이벤트 트리거 + 사용량 과금이 맞는 워크로드.
- API 서버에서 동기 처리 시: 업로드 응답 지연 + CPU 바운드 작업이 요청 스레드 점유.

**Q. 스트리밍 처리(PassThrough)를 왜 했어요?**

- Lambda 메모리에 원본 전체 적재 없이 청크 단위로 변환 → 메모리 상한 대비 안정성 + 두 variant 병렬 생성.
- 꼬리 대비: Sharp 내부 동작상 포맷별 전체 버퍼링 여부 등 한계를 물으면 아는 범위 내에서 정직하게.

**Q. DLQ에 쌓인 실패 건은 어떻게 처리해요?**

- **사전 확인 필요**: DLQ 모니터링/재처리 프로세스 실제 존재 여부. "쌓아두기만 한다"면 "현재는 추적 목적이고, 재처리 자동화가 다음 단계"로.

**Q. 확장자 없는 키에서 Sharp 포맷 감지 실패 버그 겪었다던데?** (경험 기반 자연 질문)

- 실제 겪은 버그: S3 키에 확장자 없어 대부분 invocation이 조용히 스킵 → CloudWatch 로그 분석으로 확인 → 수정.
- "조용한 실패(silent failure)"를 로그로 잡아낸 경험 — 관찰 가능성 서사와 연결 가능.

## 매력적인 포인트와 올바른 답변 방향

- **매력**: 압축에서 멈추지 않고 **이미지 생애주기 전체**(업로드 → 변환 → 서빙 → 원본 아카이빙)를 설계. "썸네일 만들었어요"에서 끝나는 주니어와의 차이.
- **주의**: 비용 절감을 금액으로 주장하지 말 것. 용량 실측(82%)과 보관 등급 전환(구조)까지만. 청구서 숫자를 물으면 "운영 초기라 절대 금액은 작고, 구조적으로 절감되는 설계를 갖춘 것"으로.

# Orbits — 이미지 업로드 원자성 문제 + 자동 정리 체계

## 변경점

- 문구 압축 및 구조 정리 (핵심 내용 유지)
- "AFTER_COMMIT 이벤트로 롤백된 이미지가 영구 보존되는 역설 방지" 명시

## 이야기할 수 있는 면접 대화 포인트

**Q. 미아 객체가 왜 "구조적으로" 발생한다는 거예요?**

- Pre-signed URL 방식은 발급(서버)과 업로드(클라이언트→S3)가 분리된 두 개의 독립 작업 → 하나의 트랜잭션으로 묶을 수 없음 → 업로드만 되고 확정 안 되는 객체가 반드시 생길 수 있는 구조.
- "버그가 아니라 아키텍처의 속성"이라고 말하는 것이 포인트.

**Q. 해결을 왜 애플리케이션이 아니라 인프라(S3 Lifecycle)에서 했어요?**

- 앱 레벨 정리 배치의 숨은 비용: 스케줄러 운영, 실패 처리, S3 목록 조회 비용, 앱 장애 시 정리 중단.
- 태그 + Lifecycle: AWS가 실행을 보장, 앱 상태와 무관, 코드 제로.
- "상태 관리 책임을 옮겼다" — 총 소유 비용 기준으로 가장 작은 해법.

**Q. AFTER_COMMIT이 왜 필요했어요? 그냥 저장 로직에서 태그 갱신하면?**

- 트랜잭션 내 태그 갱신(외부 API 호출) 시: ① 롤백돼도 S3 태그는 갱신됨 → 미확정 이미지가 confirmed로 영구 보존되는 역설 ② 외부 호출이 트랜잭션을 길게 잡음.
- TransactionalEventListener(AFTER_COMMIT)로 커밋 확정 후에만 태그 갱신.
- 꼬리 대비: "커밋 후 태그 갱신 자체가 실패하면?" → confirmed 태그가 안 붙은 채로 남아 3일 후 Lifecycle 삭제 대상이 됨 — **이 실패 모드의 처리(재시도? 감지?)를 사전 확인할 것. 가장 깊은 꼬리 질문.**

**Q. DB Insert를 저장 확정 시점으로 늦추면, 그 전에 업로드된 이미지 정보는 어디에?**

- 클라이언트가 키를 들고 있다가 확정 시 전달하는 구조라면 그 흐름 + 위조 키 검증(실제 존재 확인 등) 여부까지 답변 준비.

## 매력적인 포인트와 올바른 답변 방향

- **매력**: 이 이력서에서 문제 인식 수준이 가장 높은 항목. "분산된 작업 간 원자성 부재"라는 추상 문제를 식별하고, 보상 로직이 아니라 **설계로 차단 + 인프라로 위임**한 것. AFTER_COMMIT 역설까지 짚은 건 트랜잭션 경계 이해의 증거.
- **주의**: 이 항목은 깊게 파일수록 유리하므로 먼저 꺼내도 좋음. 단, "태그 갱신 실패 모드" 답변은 반드시 사전 확인.

# 공통 — 프로젝트 전반에 나올 수 있는 질문

**Q. 전부 사이드/교육 프로젝트인데, 실제 운영 트래픽 경험은 없네요?**

- 정면 인정 + 재프레임: "대규모 운영 트래픽 경험은 없다. 대신 작은 규모에서도 측정 조건을 고정하고 before/after를 남기는 습관을 만들었고, 그 방법론은 규모와 무관하게 이전된다. 규모가 주는 문제(분산 정합성 등)는 각 해법의 이관 기준으로 이미 정의해뒀다."
- 이력서 전체가 이 답의 증거로 작동함.

**Q. 팀에서 본인 역할은? 혼자 다 한 것처럼 쓰여 있는데.**

- 항목별로 본인 주도/협업 범위를 미리 구분해둘 것. 4인 백엔드(Pickeat)에서 각 항목의 실제 오너십을 부풀리지 말 것 — 같은 팀원이 면접관 인맥일 수 있다.

**Q. 가장 어려웠던 문제는? / 실패한 경험은?**

- 실패 후보: Sharp 확장자 감지 실패로 대부분 invocation이 조용히 스킵된 버그(발견까지의 과정), 지표 스위칭(p99→평균) 측정 설계 미흡.
- "실패 → 배운 것 → 이후 바뀐 행동" 3단 구조로.

**Q. 왜 백엔드예요?**

- 자기 언어로 준비. 이 문서 범위 밖이지만 반드시 나옴.
