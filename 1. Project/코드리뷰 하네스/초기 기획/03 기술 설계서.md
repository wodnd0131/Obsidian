## 저장소 구조

`data/eval/`은 평가 전용이라 프롬프트를 고칠 때 열지 않는다. `data/raw/`는 원문이므로 공개 저장소에 올리지 않는다.

```text
review-harness/
├── CLAUDE.md                  # 05 AI 팀 온보딩 문서
├── .claude/agents/            # 06 역할 카드 (AI 팀원별 지시서)
├── docs/                      # 01~04 문서 사본, 07 로그
├── data/
│   ├── raw/                   # 수집 원문 (git 제외)
│   ├── build/                 # 카드용 PR
│   ├── tune/                  # 튜닝용 PR
│   └── eval/                  # 평가용 PR + 정답 라벨 (프롬프트 작업 중 열람 금지)
├── cards/<mission>/           # 확정된 근거 카드
├── prompts/v0/, prompts/v1/   # 버전별 프롬프트 (수정 시 새 버전 폴더)
├── runs/<날짜>-<버전>/          # 실행 결과, 지표, 비용 기록
└── src/main/java/...          # 수집, 생성, 검증, 플래너, 평가 하네스
```

## 핵심 데이터 형식

세 형식만 정해 두면 생성, 검증, 평가가 서로 다른 단계여도 같은 기준으로 연결된다. 필드 이름은 P1에서 확정하고, 바꾸면 07 로그에 남긴다.

**근거 카드**: 미션 하나에서 짚을 리뷰 포인트 하나. 사람이 검수해 `confirmed`가 된 카드만 v1이 쓴다.

```json
{
  "cardId": "M2-07",
  "mission": "M2",
  "point": "검증 로직이 도메인 객체 밖에 있음",
  "why": "미션 의도: 객체가 자기 상태를 스스로 책임지게 하는 연습",
  "lookFor": "컨트롤러·서비스에서 도메인 값을 검사하는 코드",
  "sourceRefs": ["mission/M2.md#요구사항-3", "build/pr-12#comment-3"],
  "frequency": 5,
  "status": "confirmed"
}
```

**지적(Finding)**: 에이전트가 낸 지적 하나. v0에서는 `cardId`가 비어 있을 수 있다.

```json
{
  "findingId": "run-1021-v1-pr42-03",
  "pr": 42,
  "cardId": "M2-07",
  "file": "src/main/java/racing/Car.java",
  "startLine": 18,
  "endLine": 22,
  "quote": "if (name.length() > 5) {",
  "comment": "이름 길이 검사가 Car 밖에 있으면 ...",
  "round": 1
}
```

**판정 로그**: 사람이 지적마다 내린 판정과 회차별 소요 시간.

```json
{
  "findingId": "run-1021-v1-pr42-03",
  "decision": "edit",
  "dropReason": null,
  "roundTiming": {"pr": 42, "round": 1, "startedAt": "...", "postedAt": "..."}
}
```

`decision`은 adopt(그대로 채택), edit(고쳐서 채택), drop(폐기) 중 하나다. drop이면 `dropReason`에 irrelevant(미션 범위 밖), wrong(틀림), duplicate(중복), low-value(가치 낮음) 중 하나를 적는다.

## 제품 안 구성 요소 명세

LLM을 쓰는 구성 요소는 카드 생성기와 리뷰 생성기(v0·v1) 둘뿐이고, 나머지는 모두 코드다. 여기서 말하는 "에이전트"는 제품 안에서 돌아가는 구성 요소다. 개발을 돕는 AI 팀원은 06 역할 카드에서 따로 정의한다.

|   |   |   |   |
|---|---|---|---|
|구성 요소|종류|입력 → 출력|규칙|
|수집기|코드|GitHub PR·코멘트 → 익명화한 JSONL, 3분할|작성자는 해시로 바꾼다. 분할 기준을 기록한다|
|카드 생성기|LLM|미션 문서 + 카드용 PR 리뷰 → 카드 초안|카드마다 근거 원문 위치(`sourceRefs`)가 필수. 사람이 확정해야 쓰인다|
|리뷰 생성기 v0|LLM|PR diff + 미션 문서 → 지적|근거 제한 없음. 비교 기준선|
|리뷰 생성기 v1|LLM|PR diff + 확정 카드 → 지적|카드에 없는 지적은 내지 않는다. 해당하는 카드가 없으면 빈 배열|
|검증기|코드|지적 → 통과·탈락과 사유|아래 검증 규칙|
|회차 플래너|코드|통과한 지적 → 회차별 초안|최대 3회차, 회차당 [빈칸: 3]개 이하, 카드 `frequency` 높은 순, 같은 카드 중복 제거|
|평가 하네스|코드|버전 + 평가셋 → 지표, 실패 사례|실행마다 모델명, 프롬프트 버전, 비용 기록|

**검증 규칙**

1. 출력이 지적 JSON 형식과 일치한다.
2. v1에서는 `cardId`가 확정 카드 목록에 있다.
3. `file`이 PR diff에 있고, 줄 범위가 변경된 부분 안에 있다. [검토: 변경 줄 주변 몇 줄까지 허용할지]
4. `quote`가 해당 줄 범위의 원문에 그대로 있다. 공백 차이는 무시한다.
5. 탈락하면 사유를 담아 1회 다시 요청한다. 그래도 탈락하면 폐기하고 사유를 기록한다.

검증기는 지적에 근거가 붙어 있는지만 확인한다. 지적이 옳은지는 사람이 판정한다. 이 경계를 결과 리포트에도 그대로 적는다.

## 초기 설계 결정

아래 결정은 P0 착수 시점의 판단이다. 바꾸게 되면 07 로그에 이유와 함께 남긴다.

|   |   |   |
|---|---|---|
|결정|이유|다시 볼 조건|
|검증과 회차 배분은 LLM이 아니라 코드로 한다|결과가 매번 같아야 버전 간 차이를 측정할 수 있다|코드 규칙으로 표현할 수 없는 판단이 필요해질 때|
|PR을 카드용, 튜닝용, 평가용으로 3분할한다|카드를 만든 리뷰로 다시 평가하면 재현율이 부풀려진다|데이터가 너무 적어 3분할이 불가능할 때 (그 사실을 결과에 명시)|
|정답 라벨은 사람이 에이전트 실행 전에 확정한다|결과를 본 뒤 라벨을 정하면 판단이 결과 쪽으로 기운다|없음|
|코멘트 게시는 사람만 한다|리뷰이가 받는 말에 대한 책임은 리뷰어에게 있다|없음|
|모델 1개로 v0·v1을 모두 돌린다|모델을 바꾸면 통제 장치의 효과와 섞인다|모델 비교 자체를 실험할 때 (별도 실행으로)|

## 데이터 처리와 보안

리뷰이의 코드와 다른 리뷰어의 코멘트는 내 데이터가 아니다. 허락받은 범위에서만 쓴다.

- 수집 전에 허락받은 범위(대상 저장소, 사용 목적, 외부 LLM 전송 여부)를 07 로그에 기록한다.
- 작성자 계정명과 실명은 수집 단계에서 해시로 바꾼다. 원문은 `data/raw/`에만 두고 git에서 제외한다.
- API 키는 환경 변수로만 읽고 저장소에 커밋하지 않는다.
- 공개 저장소로 바꾸려면 `data/`와 `cards/`의 원문 인용을 빼거나 허락을 다시 받는다.
- 결과 리포트나 자소서에 리뷰이 코드를 그대로 싣지 않는다.
